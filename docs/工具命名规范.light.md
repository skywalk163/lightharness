# 工具命名规范（W2 / T2.1）

> 本卡只产出**方案与映射表**，不改注册表；改名与别名落地在 W2/T2.2（T-0502）。
> 基线：lightharness `main` @ 2026-11-26，`组装注册表()` 实测 **160** 个工具。
> 上游依赖：T-0496 的 `domain` 元数据（`src/工具面装配.light §9`），本规范不另造域。

## §0 现状与要解决的问题

模型面工具名现在是三套混着来：

1. **核心中文名**：`读文件` / `写文件` / `编辑文件` / `搜索文件`；
2. **上游英文名**：`bash` / `web_search` / `web_fetch` / `skill` / `todo_write` / `job_start` / `present`；
3. **插件中文名**：`压缩选块` / `上下文装配报告` / `工作流状态查询` / `桌面驱动CUA协议`。

名字里既不统一语言，也不统一“域 + 动作”的信息密度；被按登记序引用时更退化成只剩编号（`tool_20` / `tool_66`），
模型只能靠 description 反推用途 —— 这正是路由准确率低、思考开销大的直接来源。

本规范给出一套**可机器校验**的目标名：`<域>.<动作>`，并为全部 160 个工具产出 `tool_NN → 语义名` 映射表，
作为 T-0502 改名的唯一依据。

## §1 命名形式

```
<域>.<动作>
```

- **域前缀**：直接取 T-0496 的 `domain` 枚举原样（`host` / `file` / `workflow` …），
  唯一例外是 `横切 → xcut`（理由见 §2.2）。
- **动作**：小写 ASCII 蛇形（`[a-z][a-z0-9_]*`），动宾结构，1–2 个词，
  动词取自 §3.1 词表，名词用**被操作对象**而不是实现细节（`select_blocks` 而不是 `do_compact_step2`）。
- **长度**：整体 ≤ 40 字符；动作 ≤ 24 字符。
- **禁止**：大写、连字符、空格、中文、数字开头、连续下划线、多于一个点。
- 例：`file.search`、`ctx.select_blocks`、`workflow.query_status`、`xcut.normalize_path`。

域前缀让模型先收敛到“这是哪一类能力”，动作再区分“这一类里干什么”，两层信息互不重叠。
这也为后续分层披露（T-0498 的 tier）与按域查询（T-0496）留了同一条主轴。

### §2.1 MCP 透传不进本表

`mcp__<server>__<tool>` 的域由 T-0496 按 `mcp_<server>` 动态解析，名字由上游服务器决定，
本规范不接管、不改名，也不计入 160。T-0502 只需跳过 `mcp__` 前缀。

### §2.2 为什么 `横切 → xcut` 是唯一转写

`横切` 是 T-0496 里唯一的中文域名，而函数名必须是 ASCII（OpenAI 兼容端点的 `tools[].function.name`
只接受 `[a-zA-Z0-9_-]`），所以必须转写一次。

- 只转写这一个，其余 23 个域原样使用 —— 不另造第二套域枚举，也不把 `横切` 拆进别的域
  （拆域会破坏 T-0496 的“横切 = 多域共用、前缀无法唯一归属”这一判定口径）。
- `xcut` 取 "cross-cutting" 的缩写，本表 13 个工具全部使用，语义单一，无歧义。
- `其他 → misc` 同样只作预留：本基线 160 个工具没有一个落在 `其他`，写在这里是为了
  T-0502/T-0503 后续新增工具时不必再改规范。

## §3 动作词表

### §3.1 动词（左列强制对齐，右列是可用变体）

| 语义 | 动词 |
|---|---|
| 读 / 取 | `read` `get` `fetch` `take` |
| 写 / 存 | `write` `set` `store` `save` `apply` |
| 列出 | `list` |
| 查询状态 | `query_*` `*_status` |
| 创建 | `create` `add` `register` |
| 删除 / 取消 | `delete` `cancel` `release` |
| 执行 / 运行 | `run` `execute` `dispatch` `submit` |
| 校验 / 判定 | `validate_*` `verify` `assess` `is_*` |
| 装配 / 组装 | `assemble` `build` `bundle` `pack` |
| 选择 / 筛选 | `select_*` `filter` |

规则：

1. 不用 `do` / `tool` / `exec` 这类无语义通配词（`shell.run` 是唯一保留的通用执行，因为它就是跑命令本身）。
2. 同域内同一动作只出现一次（`config.list` 与 `config.preset_list` 并存就是违规，后者才是合法形态）。
3. 名词用对象名，不用实现（`thread_pack` 不是 `zip_worker_state`）。

### §3.2 `workflow` 61 个工具的域内族前缀

`workflow` 是 T-0496 里最粗的域（61/160），单靠域前缀区分不出来，所以动作首词固定承担“族”标记：

| 待办 | `todo_` | 5 | `todo_write/add/complete/list/delete` |
| 目标 | `goal_` | 4 | `goal` `goal_create/advance/list` |

| 终端 | `terminal_` | 4 | `terminal_open/write/read/close` |
| 缓冲 | `buffer_` | 2 | `buffer_write/read` |

而路由所需的二级信息由动作提供。

## §4 `tool_NN` 的编号口径

本表为 `tool_NN` 定的口径只有一条：

> `NN` = `组装注册表().名单()` 的 **0 基登记序**，即 `tool_20` 表示名单里第 20 个（从 0 数）工具。

依据：T-0496 判据（`tests/test_T0496_domain字段.py`）已经把这个顺序当成可复核事实钉住了 ——
`file` 子集恒为 `读文件, 写文件, 搜索文件, 编辑文件, 订阅文件变更`、`shell` 子集恒为
`bash, SSH执行, 运行用例表, 执行Python脚本`，实际就是登记序切片。本卡实测同样得到：

- `tool_20/21/22/23` = `压缩选块 / 压缩摘要 / 上下文装配 / 上下文装配报告`（全是 `ctx`，编号完全无语义）；
- `tool_66/67/68` = `工作流提交 / 工作流状态查询 / 工作流汇总`（全是 `workflow`）。

因此映射表里每行同时给 `tool`（编号）、`现名`（注册表真名）、`域`、`语义名`、`兼容`，
任何一个消费方用编号还是用现名都能对上，且两者的一致性由判据强制（见 §6）。

**编号不是别名**：`tool_NN` 只是文档侧的引用键，注册表里从来没有这个工具名，
T-0502 **不得**把 `tool_NN` 注册成别名（否则 160 个无语义工具名会重新进模型面）。

## §5 兼容策略

> T-0503 已把中文名的**展示/调用定位**单列 §10；本节 27 条别名名单不变。

每个工具只允许两种取值，且必须逐条标注：

### §5.1 `保留别名`（27 个）

名单 = **T-0477 基础白名单 ∪ 只读白名单 ∪ 既有判据/文档引用**，逐个都有“不能断”的理由：

| 来源 | 工具 | 理由 |
|---|---|---|
| 基础白名单（22） | `bash` `读文件` `写文件` `编辑文件` `搜索文件` `job_start` `job_output` `job_kill` `skill` `技能列表` `web_search` `web_fetch` `present` `todo_write` `目标` `派发子任务` `收集子任务结果` `提问提交` `回答提交` `待答列出` `答案取出` `作业状态查询` | 系统提示的逐工具指导段（`tool:bash` / `tool:read` / `tool:edit` …）与预设白名单直接按名引用；改名后若不留别名，提示词与白名单会同时指向不存在的名字 |
| 只读白名单（+2） | `技能取用` `网页抓取` | `brainstorm` 预设只读面按名引用 |
| 既有判据/文档（+3） | `SSH执行` `运行用例表` `执行Python脚本` | T-0496 判据把 `shell` 子集写成固定四条；`docs/快速开始.md` 等文档有同名示例 |

### §5.2 `直接改名`（133 个）

其余全部工具：无提示词引用、无白名单引用、无既有判据断言，改名即可，不留别名。
判定依据可复核 —— 27 个保留名的来源都能在 `src/工具面装配.light §5.5`（两张白名单）与
`tests/test_T0496_domain字段.py`（shell 子集断言）里找到原句。

### §5.3 MCP 透传（不动）

`mcp__*` 既不改名也不进别名表。

### §5.4 别名机制契约（交给 T-0502 / T-0463 实现）

1. 别名是**单向旧名 → 新名**的映射，形状 `{旧名: 新名}`，只登记 §5.1 的 27 条。
2. 解析顺序：**新名直查 → 旧名别名 → `mcp__` 透传 → 未知名报错**（`TOOL_NOT_FOUND`）。
3. 别名命中必须在审计里可区分（沿用 T-0388 的“别名归一”打点口径），便于观察旧名残留量。
4. 生命周期：至少保留到 **R+2 个版本**，且当某旧名连续两个统计周期 0 命中才允许摘除；
   摘除必须同步删掉映射表对应行的 `保留别名` 标注，否则本判据会红。
5. 冲突：新名不得等于任何现存工具名或旧名（本表已校验，见 §7.1）；若后续新增工具撞名，
   新工具改用 `_v2` 后缀，不许覆盖别名。
6. 名称大小写敏感，不做模糊匹配、不做前缀补全（避免把路由失败变成“猜名字”）。

1. **`workflow` 仍过粗**（61 个）：本卡用族前缀缓解，但根治要拆域（例如 `plan` / `job` / `todo` 独立成域）。

### §10.0 结论

160 个基线工具 = 9 个上游英文名（`bash` / `web_search` / `present` …）+ 151 个中文名。151 个中文名按三层处置：

| 结论 | 条数 | 定位 | 调用路径 |
|---|---|---|---|
| `双轨` | 18 | 展示名 **+** 唯一调用别名 | 旧名 → 语义名（T-0502 别名表） |
| `展示` | 44 | 仅展示名（只读标签） | 语义名；中文名**不可调用** |
| `退役` | 89 | 不保留中文名（只留语义名） | 语义名 |

模型调用面：160/160 语义名（`<域>.<动作>`，纯 ASCII）；中文名 **0 条**进入注册表键、schema name、枚举与解析结果。

### §10.1 判断标准（新增工具照此归类）

按顺序问三个问题：

1. **用户看得见吗** —— 这个工具的名字或它的产物，会不会出现在用户侧的对话、产物清单、终端、附件、转写里？
2. **用户会用它指代吗** —— 用户是否会用这个中文词指代这项能力（与界面文案、产品术语是否一致）？
3. **已有引用吗** —— 系统提示逐工具段、T-0477 白名单、既有判据是否按这个中文名引用（§5.1）？

判定规则：

- 命中 3 → `双轨`：展示 + 别名。**别名集合不扩张**，只认 §5.1 的 27 条（其中中文 18 条）。
- 命中 1 或 2 → `展示`：中文名只作展示标签，调用恒走语义名。
- 都不命中 → `退役`：中文名不再作为任何调用键，代码里只留语义名。

`退役` 是「不再登记为调用键」，**不是把词从代码里删掉**：旧名仍登记在 `中文名治理表` 里，可审计、可回溯。
