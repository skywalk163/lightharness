## 1. 用例分析

**位置**：`tests/test_concurrency_light.py:362-372`，`Test滑动窗口接入派发::test_无窗口时行为完全不变`。

**它在测什么**：
```python
限制器 = 速率限制(1000)          # 间隔 = 1/1000 = 0.001s
async def 两次():
    await 等待令牌(限制器)       # 第 1 次：立即放行
    await 等待令牌(限制器)       # 第 2 次：需等 ~0.001s 节拍
t0 = time.monotonic()
asyncio.run(两次())
耗时 = time.monotonic() - t0
assert 耗时 < 0.05              # ← 断言点
```

**断言语义**：无滑动窗口时，`等待令牌` 不应引入额外阻塞；两次调用总耗时应远小于 0.05s。
它与孪生用例 `test_超窗口上限的调用会被阻塞`（`assert 耗时 > 0.05`，窗口=0.1s）配对，用 0.05s 做分界线。

**依赖的时序假设**：
1. `asyncio.sleep(0.001)` 在约 1ms 后唤醒事件循环；
2. `asyncio.run()` 自身开销在 ~15ms 量级（无负载实测 p50=15.6ms）；
3. 两者之和远小于 0.05s 预算（余量 ~3 倍）。

**不依赖**：无文件、无端口、无共享状态、无 worker 间通信。每个用例自建独立 `速率限制` 对象。

## 4. CPU 加压探针（关键取证）

既然单文件矩阵复现不了，直接加压模拟全量争用。

### 4.1 微基准（直接复现测试时序逻辑）

脚本：`_r91/b_microbench.py`——在 Python 里直接循环 200 次 `速率限制(1000) + 两次等待令牌`，用 10 个 `while True` 进程打满 10 核。

| 条件 | min | p50 | p90 | p99 | max | ≥0.05s |
|---|---|---|---|---|---|---|
| **无负载（对照）** | 12.3ms | 15.6ms | 17.6ms | 18.9ms | 19.1ms | **0/200 (0%)** |
| **10 核满载** | 8.1ms | 31.8ms | 49.9ms | 84.0ms | 91.2ms | **19/200 (9.5%)** |

**结论**：
- 无负载时耗时分布集中在 12-19ms，离 50ms 预算很远。
- 满载时中位数翻倍到 32ms，p90 恰好卡在 49.9ms（边界），p99 达 84ms。
- **9.5% 的迭代会超过 0.05s 阈值**——这就是 R90 全量里 gw7 那次 0.053s 的来源。

### 4.2 pytest 级加压

脚本：`_r91/b_probe_pytest.py`——10 个燃烧进程 + 反复跑 `pytest <该用例>` 50 轮：
- **0/50 失败**。

脚本：`_r91/b_xdist_load.py`——6 个燃烧进程 + `-n auto` 跑整个 concurrency 文件 5 轮：
- **0/5 失败**。

**为什么 pytest 级复现率远低于微基准**：
1. 微基准在**同一进程**里背靠背跑 200 次，每次 `asyncio.run()` 的事件循环都处于"刚被调度完"的热状态；`asyncio.sleep(0.001)` 到期时进程需要重新入队，满载下调度延迟直接计入 wall-clock。
2. pytest 每次调用是**新进程**，经过数秒 import/collect 后才跑用例；Windows 调度器对已运行数秒的进程有更均匀的 CPU 分配，单次命中尾部的概率更低。
3. 全量跑时 10 个 worker 跑**不同的测试文件**（含子进程 spawn、I/O、内存压力），负载模式比纯 spin loop 更嘈杂，更容易撞上调度抖动的尾部。

pytest 级 0/50 ≠ 不复现：微基准 9.5% 是"单次迭代"的尾部概率，pytest 级每次只跑 1 次且进程状态不同，P(0 失败) 在低概率尾部下不排除。R90 全量已实抓 1 次（0.053s），即为实证。

## 5. 判定

### **(b) flaky（偶发、隔离恒绿、满负载调度抖动触发）**

证据：
1. ✅ 隔离串行 3/3 绿（本路 + R90-M）。
2. ✅ 单文件 xdist（worker 数 1/4/10、派发顺序 no/loadscope）21/21 绿。
3. ✅ 微基准满载下 9.5% 迭代超阈值（19/200），无负载 0/200。
4. ✅ R90 全量实抓 1 次：0.053s（仅超 3ms）。
5. ✅ 无确定性最小复现命令——worker 数/派发顺序单独跑都不红。

### 与 W-12 是否同根？

**同根不同枝**：
- **同根**：都是 Windows 本机满负载（`-n auto` = 10 worker × 10 核）下的**调度抖动**；都只在全量跑时偶发，隔离恒绿。
- **不同枝**：W-12 是子进程 stdout 时序（孙 PID 行在杀树截断前没出来）；W-13 是 asyncio 事件循环调度（`asyncio.sleep(0.001)` 唤醒延迟吹破 wall-clock 断言）。机理不同，修复方向不同。

### 建议（本路不修，交 M 路决策）

1. **断言余量不足**：`耗时 < 0.05` 的无负载基线 p50=15.6ms，满载 p90=49.9ms——余量从 3 倍压缩到 1 倍。孪生阻塞用例断言 `> 0.05`（窗口=0.1s），分界线 0.05 选在"无阻塞开销"和"窗口阻塞"之间，但没给调度抖动留余量。
2. **降频建议**：
   - 方案 A（推荐）：把阈值从 0.05 放宽到 0.15s——仍远低于阻塞路径的 ~0.1s+（阻塞用例断 >0.05，实际 ~0.1s），但给调度抖动留 3 倍余量。需同时把阻塞用例的下限从 0.05 相应抬高（如 0.08），保持分界线清晰。
   - 方案 B：不断 wall-clock 绝对值，改断"第二次调用的 sleep 时长在节拍量级"——即记录 `等待令牌` 内部实际 sleep 的时长，断它 ≈ 0.001s 而非 < 0.05s。但这需要改 `等待令牌` 返回值或加探针，动 stdlib。
   - 方案 C：给该用例加 `@pytest.mark.serial` 标记，在 `-n auto` 下强制串行跑（类似 W-01/W-08 的处理）。
3. **不建议**：循环加大 timeout、改断言为恒真——本路红线。
