# lightharness 接入 MCP 生态：从一个"能跑的复刻"到一个"能干活的 agent"

> 2026-11-18 · 对外公告 / 技术札记

## TL;DR

lightharness 今日完成两件事：

1. **首次以生产配置驱动真实大模型**（OpenAI 兼容接口，DeepSeek-chat 实测）
2. **首次通过 streamable-http MCP 协议接入生产 MCP server**（hive 集群 hived 入口），并自助从任务总线读到自己的待领任务

这标志着 lightharness 从"用中文编程语言复刻 agent 框架"的工程实践，正式变成**一个可以被大模型调度、能参与多 agent 协作的 agent 实体**。

---

## 背景：为什么这个里程碑不寻常

lightharness 立项于 2026 年 8 月，目标是用「光明」中文编程语言 1:1 复刻 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（agent 智能体框架）。

复刻的目的不是抄代码，而是**在实践里检验光明这门语言**：把原版框架的每一个子系统用光明重新实现一遍，凡是"写不出来、写出来是错的、绕不过去"的地方，就是光明需要改进的清单。

到 2026-11-18 之前，lightharness 已经完整实现：

- 工具注册与执行、模型控制、流式输出
- 并行任务、子任务分派、分离跟踪
- MCP 客户端（stdio / streamable-http 双传输）
- 凭据链、钩子、Web 面板、会话

但这一切都跑在 examples 和 pytest 里——**框架本身没有"住"一个大模型，也没有被真实生产系统调用过**。MCP 客户端有，但只在 localhost 自产自销的 echo 服务上验过。

今晚这一切变了。

## 今天的接线

### 配置（标准 DSH 英文键）

```json
{
  "mcpServers": [{
    "name": "hive",
    "transport": "http",
    "url": "http://192.168.0.88:8790/mcp",
    "headers": {"Authorization": "Bearer <token>"}
  }]
}
```

放在 cwd 的 `mcp.json`，或用 `HARNESS_MCP_CONFIG` 指向任意路径。

### 装配

`src/总入口.light` 里的 `组装注册表()` 会自动调 `挂载MCP服务器`，把 `mcpServers` 声明的所有 server 注册进模型工具表，命名 `mcp__<server>__<tool>`，与 Claude Code / Codex / DSH 同口径。

实测输出：

```
MCP 挂载完成: 18 个工具 / 1 服务器 / 失败 0
```

### 第一次真实调用

```light
设 待领 为 调用("mcp__hive__hive_list_pending", ["agent": "lightharness-fb98", "limit": 50])
```

返回：

```json
{
  "status": "success",
  "message": "lightharness-fb98 可领 2 张卡",
  "details": {
    "tasks": [
      {"id": "T-0390", "score": 135, "reasons": ["状态可领", "仓匹配", "能力全覆盖", "优先级 P1"]},
      {"id": "T-0391", "score": 135, "reasons": ["状态可领", "仓匹配", "能力全覆盖", "优先级 P1"]}
    ]
  }
}
```

**这是 lightharness 第一次以 agent 身份从外部生产系统读到"我该干什么"的答案。**

## 对接对象：hive 任务总线

hive 是一套用 git 分支做任务总线的多 agent 协作系统，部署在本机 FreeBSD：

- 主节点 / 3 followers，leader term 3869，uptime 274526s
- 本机 MCP HTTP：`127.0.0.1:8790`（agent 入口），每 agent 一个 token
- 任务真相在 Gitea git 仓（协调仓），270 张卡在册、20 个 agent 登记在册、50 个结果
- 18 个 MCP 工具：查、领、交、abort、block、续租、留言、看板……

hive 把"MCP token"和"agent 登记"分两张表管。**这次接入的最大坑也在这里**：token enroll 只解决鉴权，agent 登记必须以 `agents/<name>.json` 的形式 commit + push 进协调仓——因为 hive MCP 每次工具调用都会在独占 clone 里 `git fetch + reset --hard origin/main`，working tree 里 untracked 的文件不进它的视野。

lightharness 今天的登记 `agents/lightharness-fb98.json` 已经 commit 进协调仓主分支（`072a76d`），从此成为 hive 集群上正式在册的第 21 个 agent。

## 顺路踩到的坑（对后来者有用）

**坑一：HTTP 头透传。** 光明的 `MCPHttpClient` 构造时接受请求头数组，但只在有头时才写入 `己.请求头`，调用时要保证每次 `HTTPPost` 都带上。第一次对接生产 token 鉴权一定要验这条路。

**坑二：错误信封一致性。** hive MCP 对 worker 越权、未登记等错误一律返回统一信封 `{status: "error", message: "...", details: {hint: "..."}}`，包装在 MCP `isError: true` 里。lightharness 的 `提取文本` 拿到 `content[0].text` 后需要再 `解析JSON` 一层，才能拿到结构化的 status/message/details——不能只看 MCP `isError` 标志，业务层错误也走同一管道。

**坑三：datetime 时区。** `hive_whoami` 在我们这次接入时报 `TypeError: can't compare offset-naive and offset-aware datetimes`——这是 hive 内部的 bug，跟我们 agent 配置里 `created` 字段带 `+08:00` 时区有关。不在接入范围内，记录一下等 hive 修。

## 意义

**对 lightharness 项目**：从"实现完框架"到"框架里的 agent 真的能被生产系统调用"，是工程完成度的一次质变。MCP 客户端在真实第三方 server 上验过兼容性、错误信封、鉴权头——这份测试是 pytest 桩给不了的。

**对光明语言**：今天跑通的关键路径里没有一处需要"用光明做不到"的妥协——配置解析、JSON 处理、HTTP 请求、并发线程、协议握手，全是标准光明语法。这是对"光明能不能写 agent 框架"这道题的又一次肯定回答。

**对多 agent 协作**：hive 集群上现在跑着 20+ 个 agent（CodeArts、DeepSeek、豆包、Trae、WorkBuddy、小浣熊……跨 Win10/Win11/macOS/FreeBSD）。今天 lightharness 正式加入了这个名单，成为第一个用中文编程语言写就的 agent。
