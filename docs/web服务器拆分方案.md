# `src/web服务器.light` 拆分方案（T-0393）

> 状态：**方案已交 + Phase 1 已安全落地**。Phase 2+ 待主控评审后再动代码。
> 基线：`src/web服务器.light` 2238 行 / 121141 字节，本仓最大 `.light` 文件。
> 原则：**薄入口 + 子模块**，每步可独立回滚；**宁可少拆，不可拆坏**。

---

## 0. 结论先行

1. **能安全拆的**：模块级「无状态纯辅助」（请求解析 / 文本切分 / CORS / 健康探针 /
   回环判定 / 环境读取）。它们不碰类、不碰模块级单例 `全局服务`，外部无反向依赖，
   已在 Phase 1 拆为 `src/web_请求辅助.light`，`web服务器.light` 同名转发导入。
2. **本轮不拆的（有硬约束）**：
   - **流式推流三件套**（`造流式响应` / `后台跑一轮` / `推流实现`）**必须留在
     `web服务器.light`**。原因：`tests/test_流式推流接线契约.py` 直接对
     `src/web服务器.light` **源码文本**做断言——要求 `从 实时流 导入 …实时队列…编码SSE帧…流块转增量帧`、
     `从 线程 导入 …线程`、`从 HTTP服务端 导入 …流发送`、`载具["服务"]`、`"服务": 己`、
     `响应["服务"] 为 己`、以及 `异步 段落 推流实现(...)` 形参恰好 3 个**全部出现在本文件**。
     抽走任一即契约变红。**这是本轮最关键的约束，拆分边界必须绕开它。**
   - **`路由处理器`（异步分派）** 与 **`全局服务` 单例** 留在入口。二者互相引用
     （处理器读 `全局服务`，单例的类型 `Web服务端` 也在本文件），抽走会引入
     `web服务器 ⇄ web_路由` 循环导入——本仓已实测过循环依赖半初始化崩溃（R105）。
   - **`Web服务端` 类的 74 个方法**：全部挂在同一个类体上（`己.` 状态自引用），
     光明语不支持把一个类的方法分文件定义。要拆只能改成「组合 + 委托」，那是
     **大爆炸重构**，违反本卡「保守分阶段」要求 → 留作后续卡。
3. 因此 `web服务器.light` 本轮**不会降到 30KB 以下**（流式 + 路由 + 巨类三者锁死体积）。
   本轮目标是：**交出清晰边界清单 + 安全拆出可拆的部分 + 零行为回归**，把巨类拆解
   留作评审后的后续卡。

## 3. Phase 1（本轮已做）：拆 B1 请求级纯辅助

### 3.1 为何这批最安全
- **无状态**：除 `处理健康检查(服务)` / `解析会话标识(服务,…)` / `加跨域(响应)` 接收
  参数外，不读不写任何全局；不碰 `全局服务` 单例，不碰 `Web服务端` 类。
- **无反向依赖**：grep 全仓 `examples/ tests/ src/`，**无任何模块** `从 web服务器 导入`
  这 9 个名字 → 抽走后对外零影响。
- **依赖极简**：只需 `从 JSON 导入 序列化JSON`；`环境变量` 是地板内置（`内置核心系统`），
  无需 import。

### 3.2 落地方式（薄入口 + 同名转发）
- 新建 `src/web_请求辅助.light`：承载上述 9 个 `段落`，`导出` 全部 9 个。
- `src/web服务器.light`：**删除这 9 个函数体**，原地改为
  `从 web_请求辅助 导入 分割字符串, 解析查询参数, …, 加跨域`。
  由于导入即把名字注入本模块命名空间，类方法里 48 处 `加跨域(…)`、`处理对话` 里的
  `解析会话标识(…)` 等**裸名调用全部照旧生效**，无需改动任何调用点。
- `导出 处理健康检查` 照旧（转发导入的名字可再导出）。

### 3.3 明确不搬的（同区段但被锁）
- `后台跑一轮` / `推流实现`：流式契约锁死（见 §0.2）。
- `造钩子头表` / `取头值` / `钩子取秘密` / `钩子当前时间` / `钩子派发` / `造钩子能力`：
  `钩子取秘密` / `钩子派发` 直接 `全局 全局服务`，搬走需把单例也搬或注入 → 与 B3 一样
  环耦合，本轮整体留在入口（webhook 关注点完整内聚在一处）。

## 4. Phase 2+（待评审）：巨类拆解路线

每步独立可回滚，每步跑对应端点 examples 确认 rc=0 再进下一步：

1. **Phase 2a**：B4 静态资源 → `web_静态资源.light`。`处理静态` 只依赖 `界面目录` +
   `文件系统`，把 `界面目录` 状态一并交给协作者，入口委托。
2. **Phase 2b**：B7 审批/权限 → `web_审批端点.light`。审批/权限 6 法依赖
   `权限管理器` / `审批管理器`（已是独立对象），最易组合化。
3. **Phase 2c**：B5 会话 CRUD + 会话模型。
4. **Phase 2d**：B6 配置/设置/快捷键。
5. **Phase 2e**：B8 提供商/jet-hub/插件/引导/凭据（依赖面最广，最后拆）。

每个 Phase 引入一个协作者对象（如 `Web会话面`），入口 `Web服务端` 持有它并把
`服务.处理X` 委托过去，`路由处理器` 的 `服务.处理X(…)` 调用点**一行不改**。
