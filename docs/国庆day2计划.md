### 0.2 本计划（day2）的体量口径

用户明确要求：**day2 计划的工作量 = 7 天计划的量**，但因 agent 极快，预期压缩到 **约半天** 完成。
所以本计划**不按「天」排期**，而是把与 7 天计划**等量的工作量**打包成
「3–4 条串行线 + 3 条并行轨道 + 1 道验收屏障」，并显式标注「预期压缩到半天」。

> ⚠️ **压缩前提（必须写清）**：压缩成立的前提是 **沿用 7 天计划已验证的执行模型**——
> 本会话 Agent 工具少量并行（2–3 路）+ team lead 强制复现 + 子代理谎报防护 + 每路独立 worktree。
> 若某轨遇到真阻塞（如 1.5 链路、github 代理），按各轨「砍线」降级，**不拖屏障 D**。
>
> ⚠️ **v1.1 补：压缩的算术前提也要写清**（原 v1.0 自相矛盾，见 §十二-5）：
> 串行线自身估算和 = L1 2–3h + L2 2–3h + L3 2h = **6–8h**，已等于 §九 给的 6h 墙钟；L4（3–4h）与三轨（2–3h×3）在时间上没有容身之处。
> → 「约 6 小时」应读作**并行后的墙钟**，且**依赖 §四 快门条件化**（否则门窗口会把它拖到次日）。

## 七、复用纪律（从 7 天计划继承 + v1.1 新增，day2 必须遵守）

1. **三元判据**（failed + skipped + passed 任一劣化即 FAIL）：现行门（`scripts/回归基线.py:187`）只看 failed，对「passed 变 skipped」失明 → **必须人工比对三元**。
2. **`--mode full` 基线**：`--mode` 默认 `fast`，编译器改动日与验收日**必须显式 `--mode full`**，禁止跨剖面 diff。
3. **safe-delete 护栏**：长跑必带 `CODEBUDDY_SAFE_DELETE_ENABLED=0`，否则成片假红（7 天计划 Day1 血泪坑）。
4. **子代理谎报防护**：每路契约必须带回「真实命令 + 退出码」，team lead 亲自复现，不信任口头结论。
5. **每路独立 worktree + 独立分支**，出口各打 `track-A/B/C-done`，防同树互踩（R109 B 线教训）。
6. **门互斥窗口**：0.82 门只许 12:30/18:00 两批跑，同一时刻全环境仅一个门。（**v1.1：此约束只适用于并行期**；串行线内的快门见 §三）
7. **🆕 未入账的 flaky 不算豁免**：`light-merge/tests/ci_environment_reds.txt` 的入账口径要求「一手取证（隔离复跑 2 次 + 错误签名 + 复现命令）」，且「**未登记文件/平台下的失败仍硬判回归**」。今后任何「已知 flaky」放行都必须先入账；L1 的两条此前**未入账**，本计划补取证。
8. **🆕 门判据禁用 `refresh-local` 自比**：台账原话「别用 `多平台矩阵.py --mode lm-full --refresh-local` 的『新增红 0』当判据：它把新基线写进 latest 再自比，**恒为 0、没有意义**。要对拍**时间戳基线**」。
9. **🆕 假红有三个来源，不能只防一个**：① safe-delete 护栏（见第 3 条）；② **xdist worker 被杀**（`[gwN] node down: Not properly terminated` → `INTERNALERROR … execnet bootstrap io.read(1) got 0`，台账实证**曾出现 507 failed 的中断产物、非真实回归**）；③ **CPU ≥80% 时 `-n 4` 仍会崩** → 跑前先过 `scripts/跑前CPU门禁.py`。Windows LM 全量标准 worker 数 = **`-n 4`**（`-n auto`/`-n 8` 有挂死史）。看到成片红先怀疑这三源，不要报回归。

## 八、🆕 必须固化的新教训（v0.3.0 发布实证）

> 这俩是 v0.3.0 发布过程踩出的**新坑**，7 天计划没写，day2 及以后必须载入风险表。

### 8.1 GitHub 同步禁止 CRLF 归一（致命）

`_push_github_tree_sync.py` v1 曾对 blob 做 `CRLF→LF` 归一 → lightharness `docs/功能对标/语言缺陷账.md`
（git 对象库里存的是 **CRLF**）github SHA `6902562ab8` ≠ 本地 `dc1f98b610`，**2001 个文件里只有 1 个漂移**，
导致 github tree 与本地 tree 不等价。

**铁律**：脚本上传 git blob 必须**原样字节**（`raw = blob_bytes`，**不** `.replace(b"\r\n", b"\n")`）。
v0.3.0 已修（LH github commit `a5c837e9d7` tree `a5c0b0a9` = 本地 `082255c` tree；**v1.1 实测复核 `git rev-parse 082255c^{tree}` = `a5c0b0a969795d…`，逐字对上**）。
→ day2 任何 github 推送脚本/动作**沿用修复版**，禁重蹈归一。

### 8.2 多远端推送必须逐 (repo,remote) 枚举复核

v0.3.0 发布时**漏推 2 处**，靠 `git ls-remote` 才抓出：
- 漏 1：lightharness 的 gitcode 远端**名叫 `origin`**（非 `gitcode`），脚本用 `git push gitcode` 直接失败（"does not appear to be a git repository"）
- 漏 2：light-merge 的 **gitea** 远端被遗忘（fast-channel 只推了 LM 本地 origin + gitcode）

**铁律**：任何多远端推送后，**逐 (repo, remote) 枚举 `git ls-remote <r> refs/heads/main` + `git ls-remote <r> <tag>` 复核 SHA**，
禁止只看 `git push | tail`（会吞掉失败，`$?` 是 tail 的退出码恒 0，出现「空输出 + rc=0 但远端无 refs」的假成功）。

> ⚠️ **远端名不统一**（day2 推送前先 `git -C <repo> remote -v` 列一遍）：
> - LH：github / myrepo(192.168.1.5) / **origin(=gitcode.com/skywalk163/lightharness)**
> - LP：github / gitcode / gitea(192.168.1.5)
> - LM：github / gitcode / **origin(=g:\github\light 本地路径)** / gitea(192.168.1.5)
> → 三仓共 **10 个远端落点**（LM 的本地 origin 算 1 个），day2 推送逐项点名，不按名字猜。
> （v1.1 实测：三仓 `remote -v` 与上表**逐字一致**；本地镜像 `g:\github\light` 的 `v0.3.0` = `d6b84a7` = 其 HEAD ✅）

### 8.3 🆕 本机对 github / gitcode **不可达**，铁律要留 API 后门

v1.1 实测：本机对 **github ×3** 与 **gitcode ×3** 的 `git ls-remote` 全部 `unable to access`（网络层），
仅 **192.168.1.5 的 gitea/myrepo 可达**（三仓 SHA 均匹配）；LM 的本地路径远端还会撞沙箱管道限制
（`sh.exe: couldn't create signal pipe, Win32 error 5`）。

**故 §8.2 的铁律在本机对 6–7 个落点**跑不动 → 计划必须写明**等价复核路径**：
- 能 `ls-remote` 的（gitea/myrepo + 本地镜像）→ 照 §8.2 执行；
- **不能的（github/gitcode）→ 走 API 等价路径复核**（沿用 `_push_github_tree_sync.py` 的 API 通道，例如 `GET /git/refs/tags/<tag>` 比对 SHA），并在报告里注明「走 API 复核，非 ls-remote」；
- 二者都不可用时，**明写「未能复核」**，不得默认成功。
