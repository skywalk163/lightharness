## test_终端PTY.light（FreeBSD 预期红，2026-08-30 登记）

- **现象**：FreeBSD runner 上该用例 rc=1，断言失败
  `输出应含计算结果 3，实际=expr 1 + 2`——
  PTY 会话写入 `expr 1 + 2` 后只回显了命令本身，没读到 shell 的执行结果 `3`。
- **根因**：伪终端 / 外壳交互在 FreeBSD 上脆弱（写入后读取时序或行尾处理，
  导致 shell 未真正执行命令）。属 harness 层 PTY 实现既有缺陷，**平台相关**
  （Windows 本地用 ConPTY 可绿，故仅 FreeBSD 登记预期红）。
- **与 P0-2 关系**：**无关**。本次 P0-2 改动对 `test_终端PTY` 零影响——
  `light run` 默认走 src 后端；`codegen_typed.py`（原生后端）对 src 零作用，
  `code_generator.py` 仅新增 `码位/字符自码位/十六进制` 三个纯 additive 映射；
  `终端.light` 未被本次改动触及，其 `文本.encode`/`全部.decode` 是 PTY 模块正常字节处理。
- **登记动作**：`tests/test_回归.py` 的 `EXPECT_RED` 仅在非 Windows（FreeBSD）下
  包含 `test_终端PTY.light`，使 CI 判其「预期红=通过」。
- **后续处置（留待以后）**：在 FreeBSD runner 上单独调试 `终端.light` /
  `stdlib/伪终端.light` 的 PTY 交互（写入-读取时序、行尾 `\n` vs `\r\n`、
  sh 的 `expr` 执行）。修好后删除 `EXPECT_RED` 登记项，该用例即恢复硬判绿。
- **反向校验**：若某次 CI 该用例意外变绿（FreeBSD 上 PTY 修好），
  `test_回归.py` 的 `assert rc != 0` 会因「预期红却绿」而失败，倒逼删除本登记。
