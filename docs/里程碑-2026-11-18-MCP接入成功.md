# 光明照进现实：lightharness 第一次用大模型、第一次装上 MCP

> 2026-11-18 晚，一个值得记下的夜晚。

## 一句结论

**今天，lightharness 第一次用真实大模型，第一次挂上外部 MCP server，第一次自助从 hive 任务总线读到 2 张待领任务卡。**

从「写代码复刻 DeepSeek Harness」到「自己就是一个能被大模型调度的 agent」，这条线今天接通了。

## 之前我们有什么

lightharness 是「用光明中文编程语言 1:1 复刻 DeepSeek Harness」的工程。从 8 月到现在，我们一路把

- 工具调用、模型控制、并行任务、子任务分派
- 凭据链、MCP 客户端（stdio / streamable-http 双传输）
- 钩子、分离跟踪、会话、Web 面板

用光明一行一行写出来。测试一直在跑、绿得很整齐，但它有一个隐含的尴尬：**框架能跑，框架里没"住"一个大模型，也没有外部世界给它喂活**。

`test_mcp_prod.light` 是桩回归，跑的是 cwd 里一份测试 `mcp.json`，2 个 echo 工具。
`test_mcp_http_real.light` 是 HTTP 真机，但服务端是我们自己写的 `examples/mcp_http服务器.py` —— 自产自销。
`test_mcp.light`、`test_mcp接线.light` 也是桩。

**框架完整，但没跟真实生产系统握过手。**

## 今天发生了什么

3 个改动，一次接通：

**1. 大模型接上了。** `.env` 里填的就是 `OPENAI_BASE_URL=https://api.deepseek.com/chat/completions` + `deepseek-chat`。从 mock 到真模型这一步其实早通了，但今天它和 MCP 同时在线才有意义——大模型第一次可以伸手去够框架之外的世界。

**2. MCP 客户端对接生产 MCP server。** 不是桩、不是自产自销的 echo，是 **hive 集群的 hived MCP HTTP 入口**——`http://192.168.0.88:8790/mcp`，跑在 FreeBSD 真机上，背后是一个真正在管任务的系统：

```
$ curl http://192.168.0.88:8790/healthz
{"ok": true, "service": "hive-mcp", "status": {"enabled": true, ...,
  "cache": {"cards": 270, "agents": 20, "claims": 1, "results": 248}}}
```

**3. `mcp.json` 第一次装进真实配置。** 标准 DSH 英文键，一份 token，一行 `挂载MCP服务器`，18 个工具就出现在模型工具表里：

```json
{
  "mcpServers": [{
    "name": "hive",
    "transport": "http",
    "url": "http://192.168.0.88:8790/mcp",
    "headers": {"Authorization": "Bearer <token>"}
  }]
}
```

```
$ python3 运行.py examples/_probe_hive_mcp.light
MCP 挂载完成: 18 个工具 / 1 服务器 / 失败 0
PENDING_FOR_ME={"status":"success","message":"lightharness-fb98 可领 2 张卡",
  "details":{"tasks":[T-0390 score=135, T-0391 score=135]}}
```

## 踩过的两个坑（也值得记）

**坑一：token ≠ 登记。** MCP token enroll 完只是凭证，hive 还要求 `agents/<name>.json` 进 git。我一开始把 agent 配置写盘、没 commit，MCP 工具调用就一直报「没有登记 agent lightharness-fb98」。原因很直接：hive MCP 每次工具调用都在独占 clone 里 `git fetch + reset --hard origin/main`，working tree 里 untracked 的文件根本进不了它的视野。**协调仓 = git 真相**，这条hive 立的规矩我们今天亲身验证了一次。commit + push 完，立刻通。

**坑二：光明自己的 MCPHttp 客户端要吃 HTTPS。** 我们 `mcp客户端.light` 的 `MCPHttpClient` 早就实现了 streamable-http，但一直只在测试里喂 localhost。今天喂 `http://192.168.0.88:8790/mcp` + `Authorization: Bearer` 头一次跑就过——握手、tools/list、tools/call、错误信封，全都按 DSH 那一套走通了。

## 这意味着什么

**1. lightharness 不再只是"能跑的复刻"。** 它现在能被大模型驱动、能伸出去够外部生产系统、能拿到自己"该干什么"的答案。

**2. MCP 客户端从"实现完"变成"用起来"。** `MCPHttpClient` 第一次跟非自家生产的 MCP server 对话，协议栈的兼容性、错误信封、鉴权头，全都在真实环境里验过一遍。

**3. 打通了"agent 干活"这最后一公里。** 之前 hive 集群上别的 agent 接任务、交活，今天轮到 lightharness 自己也进了这个名单：`agents/lightharness-fb98.json` 已经 commit 进协调仓，lightharness 现在是一个**正式在册**的 hive agent。

## 一点感想

当初立项，动机很朴素：「光明这门语言到底能不能写出一个像样的 agent 框架？写不出来、写出来是错的、绕不过去的地方，就是光明需要改进的清单。」

今天这一刻，某种意义上就是那道题的答案：**光明写出来的 agent 框架，能用大模型，能接 MCP，能进生产集群领任务。** 剩下的不是"能不能"，而是"好不好用、稳不稳、生态全不全"——这是另一种类型的问题，也是让人更踏实的那种。

从 examples 里的桩，到 hive 里 `lightharness-fb98` 这行登记，中间隔着 R50、R62、R87、R111、R155、R176、R177、R221 一长串版本号、一长串踩坑文档、一长串凌晨的 debug。今晚它终于落地了。

可喜可贺。下次开会应该开香槟。
