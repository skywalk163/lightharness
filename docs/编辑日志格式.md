# 编辑日志格式（schema v1）

> 一条记录 = **对同一个文件的一次编辑 + 编辑前后各一次 `light ai check` 的结果**。
> JSONL，一行一条，append-only。代码：`scripts/编辑日志.py`（纯标准库，单文件可跑）。
> 真实写入路径：`scripts/安全替换.py --out ... [--check]`。

## 一、为什么必须有这个格式

`lightprism/docs/样本导出.md` §2.2 已经证明：`light ai check` 的报错归档**结构上导不出修复样本**。
`source_hash` 是对**出错那一刻**的源码算的：

- 代码没改 → hash 能匹配 → 现跑必然仍失败；
- 代码改好了 → 现跑会通过 → 但 hash 变了，永远匹配不上那条记录。

实测（同文档）：`打印(甲[9])` 改成 `打印(甲[0])` 后，hash 从
`3f8e1a3acc644768` 变成 `1284d1e5c731b464`，记录直接落到 `skipped_no_source`。

所以 `V:ERR=…` → `V:PASS` 的配对只能来自**记录了编辑动作**的日志。
本格式就是那个来源；`docs/样本导出.md` §4 里写的「该格式目前不存在」，由本文件补齐。
下游导出器（LightPrism 侧，另一张卡）只应把 `outcome=fixed` 的记录当修复样本：
`still_failing` / `regressed` / `unknown` 都不构成「从坏到好」的因果证据。

## 二、落盘位置与写入约定

| 项 | 约定 |
|---|---|
| 目录 | `$LIGHTHARNESS_EDIT_LOG_DIR`；未设置时 `~/.lightharness/edits/` |
| 文件名 | `<YYYY-MM>.jsonl`（按记录 `ts` 的月份分文件） |
| 编码 | UTF-8，`\n` 换行；一行一个 JSON 对象 |
| 写入方式 | **append-only**（`open(..., "a")`），从不回写、不重写历史行 |
| 去重键 | `(file_hash_before, file_hash_after, ts)` 三元组，命中则不写第二次 |
| 多节点 | `event_id = <hostname>-<microsecond>-<rand>`，供多机合流时再去重 |
| 拒绝 | 追加时若发现历史行已有空行 / 非法 JSON，直接报错拒绝追加，不静默跳过 |

`record()` 在写入前先跑完整 schema 校验；非法记录根本进不了文件。

## 三、字段表（全部必填，缺一即非法）

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | int | 固定 `1` |
| `event_id` | str | `<hostname>-<microsecond>-<rand>`，多节点去重 |
| `ts` | str | ISO8601 **带时区**，如 `2026-11-12T17:30:00+08:00` |
| `session_id` | str \| null | 一次会话；没有就 `null`，不猜 |
| `task_id` | str \| null | 任务 / 卡片 id，用于把多步编辑归到同一任务 |
| `agent` | str \| null | 谁做的编辑 |
| `repo` | str | 仓库名（默认 `lightharness`） |
| `file` | str | **repo 相对路径**；拒绝 `/` 开头、盘符、UNC、`..` 穿越；落在 repo 外时只保留文件名 |
| `file_hash_before` | str | 换行归一化后 `sha256(...)[:16]`，与 light 归档同口径 |
| `file_hash_after` | str | 同上 |
| `edit_kind` | str | **`FR` / `RW` / `PATCH`**，与 LightPrism 决策点 `EDIT` 的选项集对齐 |
| `diff` | obj | `{unified: str}` 或 `{before: str, after: str}`；可带 `truncated: bool` |
| `check_before` | obj \| null | `{ok, code, severity, stage, message}` |
| `check_after` | obj \| null | 同上 |
| `outcome` | str | `fixed` / `still_failing` / `regressed` / `unknown`，**由前后 check 推导，不许人填** |
| `light_version` | str | 复现所需；拿不到时空串（不编造） |
| `backend` | str | 复现所需；拿不到时空串 |

允许附加字段（如 `replaced`、`target`），但上述字段一个都不能少。
`check_*` 对象的 `code` / `severity` / `stage` / `message` 允许为 `null`（例如 `ok=true` 时没有诊断），
但 `ok` **必须是布尔值**。

### 3.1 hash 口径

```python
sha256(text.replace("\r\n", "\n").replace("\r", "\n").encode("utf-8")).hexdigest()[:16]
```

与 `light/cli/light.py` 的报错归档完全一致。口径对齐是硬要求：下游要靠
`file_hash_before` 与归档里的 `source_hash` 认出「同一份坏代码」。
本机实测（2026-11-12）：坏文件 `3f8e1a3acc644768`，改好后 `1284d1e5c731b464`，
与 `docs/样本导出.md` §2.2 的数字一致。

### 3.2 diff 与路径打码

- 默认写 `{before, after}` 全文（换行已归一化）；单侧超过 **20000 字符**时截断，
  并置 `diff.truncated = true`。截断是显式标记，不是静默丢内容。
- `diff` 内容、诊断 `message`、附加字段里的**本机绝对路径一律打码**成 `<PATH>` / `<HOST_PATH>/`。
  日志里不允许出现 `/home/...`、`C:\Users\...` 这类目录结构。

### 3.3 edit_kind 怎么选（不许乱标）

| 值 | 实际行为 |
|---|---|
| `FR` | 逐个标识符替换：目标串与替换串都是单个标识符，词法感知地只改代码里的标识符出现处 |
| `RW` | 全文件重写：目标串就是整份文件内容，整份被换掉 |
| `PATCH` | 整串替换：对文件里的目标子串做字面替换（本工具默认行为） |

`scripts/安全替换.py` 的 `--edit-kind auto` 按上表自动判定，也可用
`--edit-kind FR|RW|PATCH` 显式声明。判定依据写在代码里，可复核。

### 3.4 check_before / check_after 从哪来

`--check` 时，编辑前后各跑一次：

```sh
python <light>/cli/light.py ai check <file> --run --json --no-corpus
```

`--no-corpus` 保证不污染 `~/.light/error_corpus`；`--run` 是必须的（不带 `--run`
只做语法检查，L3001 越界这类运行期错误会被判成 `ok: true`）。
取 stdout 里最后一个结果 JSON，再取**第一条 `severity == "error"`** 的诊断，
映射成 `{ok, code, severity, stage, message}`。

退出码 `0` = 无 error 级诊断，`1` = 有，`2` = 用法/文件错误。
**退出码 2、超时、找不到 CLI、JSON 解析失败 → 该次 check 记 `null`**。
不传 `--check` 时两次都是 `null`。绝不手填、绝不外推。

## 四、outcome 判定规则（写死，有测试）

`outcome` 是 `check_before.ok` / `check_after.ok` 的纯函数：

| before | after | outcome | 能当修复样本 |
|---|---|---|---|
| `false` | `true` | `fixed` | ✅ 唯一有效来源 |
| `false` | `false` | `still_failing` | ❌ |
| `true` | `false` | `regressed` | ❌ |
| `true` | `true` | `unknown` | ❌ 既没坏也没修 |
| 任一为 `null` / `ok` 非 bool | — | `unknown` | ❌ |

`validate` 会把声明的 `outcome` 与推导值逐条比对；不一致直接报
「outcome 与 check 推导不一致 …（不许手填）」并给行号。
`record` CLI 读入外部 JSON 时也会重算覆盖，人手填的值不生效。

## 五、CLI

```sh
python scripts/编辑日志.py --self-test                 # 内置 4 条 fixture，不依赖外部文件
python scripts/编辑日志.py validate <path>             # 逐行校验，非法行报行号
python scripts/编辑日志.py dump --json                 # JSONL 回放（一行一条，可 | tail -1）
python scripts/编辑日志.py dump --json --outcome fixed --since 2026-11-01T00:00:00+08:00
python scripts/编辑日志.py dump --array                # 输出单个 JSON 数组
python scripts/编辑日志.py record sample.json          # 追加（outcome 仍由 check 推导）
```

`dump` 默认读日志目录下所有 `*.jsonl`，支持 `--path` / `--outcome` / `--since` /
`--until` / `--limit`；遇非法行**报错拒绝回放**，不静默跳过。
`validate <path>` 退出码：`0` = 全合法，`1` = 有非法行。

`--self-test` 内置 4 条 fixture（fixed / still_failing / regressed / unknown），
跑 schema、去重、outcome 推导、行号报错、相对路径、枚举白名单、hash 口径、diff 截断。

## 六、真实编辑路径怎么接上的

`scripts/安全替换.py`（词法感知替换 + `--out` 落盘 + 拒绝覆盖输入）是挂载点：

```sh
# 不传 --check：check_* = null，outcome = unknown（诚实，不猜）
python scripts/安全替换.py /tmp/bad.light '甲[9]' '甲[0]' --out /tmp/fixed.light

# 传 --check：编辑前后各跑一次真实 checker，outcome 由结果推导
python scripts/安全替换.py /tmp/bad.light '甲[9]' '甲[0]' --out /tmp/fixed.light --check
python scripts/编辑日志.py dump --json | tail -1
```

只在**成功写盘**后追加日志；`--dry-run`、输出到 stdout、`--no-edit-log` 都不写。
`--check` 需要 `--out`（没有落盘对象就没有「改之后」可查）。
原有替换语义与 `--self-test` 未改动，自测不产生日志。

### 6.1 本机实测证据（2026-11-12，Windows / Python 3.13.14）

坏文件 `设 甲 为 [1, 2]` + `打印(甲[9])` → 改成 `打印(甲[0])`：

```sh
$ python scripts/安全替换.py /tmp/bad.light '甲[9]' '甲[0]' --out /tmp/fixed.light --check
编辑日志: ~/.lightharness/edits/2026-11.jsonl  ← edit_kind=PATCH outcome=fixed

$ python scripts/编辑日志.py dump --json | tail -1
{"check_before": {"ok": false, "code": "L3001", "severity": "error",
                  "stage": "运行", "message": "索引错误 列表索引越界（bad:2）"},
 "check_after":  {"ok": true, ...},
 "file_hash_before": "3f8e1a3acc644768",
 "file_hash_after":  "1284d1e5c731b464",
 "file": "fixed.light", "edit_kind": "PATCH", "outcome": "fixed",
 "light_version": "光明编译器 v0.4.1", "schema_version": 1, ...}

$ python scripts/编辑日志.py validate ~/.lightharness/edits/2026-11.jsonl
校验完成: 1 条合法，0 条非法
```

两个关键点：① hash 与 `docs/样本导出.md` §2.2 的实测数字逐个一致，证明口径与 light
归档对齐；② `check_before` 取的是 `stage=运行` 的 L3001（必须 `--run`，不带 `--run`
只会做语法检查并把越界代码判成通过）。不传 `--check` 的对照实测得到
`check_before=null`、`check_after=null`、`outcome=unknown`。

## 七、禁止事项

- **不伪造日志**：checker 跑不出真实结果就 `null` + `unknown`；`outcome` 不可手填。
- **不落绝对路径**：`file` 必须 repo 相对；`diff` / 消息里的本机路径要打码。
- **不猜格式**：本文件是 schema v1 的唯一定义；下游解析器按此读，不按「看起来像」猜。
- 不引入第三方依赖；不改 `light ai check` 自身，也不动报错归档（`--no-corpus`）。
- 本仓只负责**定义并写入**格式；LightPrism 侧的解析器 / 导出器是另一张卡（跨仓，走新卡）。
