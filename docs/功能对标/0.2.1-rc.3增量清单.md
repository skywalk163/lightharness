## 0. 结论先行

1. **增量体量的真实构成与"32 万行"的字面观感差距很大。** 8583 个变更文件里，真正进入 `packages/*/src/` 且非测试的代码文件只有 **1047 个**（其中 .ts 841、.tsx 124、.css 59，其余为图片），合计 **新增 50788 行、删除 15773 行**；剩下约 7500 个文件是 README、`package.json`、`locale/*.json`、`.i18n.yaml`、Cordis catalog 再生成、`.agents` 决策笔记与 `snapshots` 快照。
2. **这不是一次"功能扩张"，而是一次"架构收敛 + 平台面扩张"。** 1487 条非 merge commit 中，`fix` 类 569 条、`test` 类 412 条，`feat` 类仅 146 条；`subagent` 包 7691 增 / 7415 删，净行数几乎为零，实为两个管理器合并。真正的新功能集中在 **CUA（计算机操作代理，106 条 commit，全仓最高）**、**模型列表发现（llm-deepseek `/models`）**、**远程访问控制（remote-access）**、**钩子协议（hook-protocol）** 四块。
3. **纯逻辑可移植面收敛为 14 项、共 47 个文件**，按工作量分三档：立即可移植 6 项（请求信任栅栏、凭据优先级、preset 选择、PTC 参数序、目标轮驱动、schedule 提醒链）、中等 6 项、大工作量 2 项（令牌计量折叠、远程访问控制）。
4. **宿主面（登记不移植）占绝对多数：约 640 个 src 文件**，集中在 client UI（119 个 .tsx）、cua-macos 的 Swift/AppKit、experimental 的 native 与 devtools、ptc-runtime、speech/browser 运行时、ssh/subprocess/sandbox。
5. **架构面共 23 条建议**，其中最需要 lightharness 决策的是：主体（Principal）与远程访问模型、工作目录集中化、one-shot/continuable 双轨合一、Cordis invariant 插件整体摘除。
6. **上一轮 A 路（R126，对齐 alpha.1）的结论有 3 处需要修正**：`client/file-upload` receipts 隔离已成为主体化改造的一部分；`schedule` 工具包迁包后仍在演进（标题简化、拒绝链加固）；`util/values/partial-json` 已在 alpha.1 判定移植，本轮未回退，仍是同一份 666 行实现。

## 6. 架构对齐建议（23 条）

### 6.1 必须决策的四条

1. **主体（Principal）与远程访问模型**（`api/remote-access`、`typert/protocol`、`subagent` 的 `principalOf`）。上游把"非 owner Peer 能调用哪些方法、能收到哪些事件"变成一等公民：业务包注册角色，访问层统一判定，客户端读自己的访问快照以隐藏 Host 会拒绝的条目。**建议**：lightharness 若要支持多客户端/多主体（远程访问、子代理、外部 Peer），需要在 `网关协议.light` 之上引入主体与资源概念，否则 §5-4 的规则无处落地。这是本轮唯一"不做则后续所有权限规则都要返工"的决策点。
2. **工作目录集中化**（新增 `session/working-directory`，删除子代理侧 cwd 解析）。**建议**：把 cwd 的解析与校验集中到会话模块一处，子代理只接收已校验值 + 独立的 `originCwd`（父源目录与子生效目录分离）。当前 lightharness 分散在 `工作区路径.light` / `工具_路径安全.light` / 子代理各处，建议合并入口，规则保留。
3. **one-shot 与 continuable 双轨合一**（`subagent-in-process-driver` 整包删除）。**建议**：lightharness 若同时存在两种子代理执行形态，统一为"每次委派都产生一个受管激活"，`kind: local | external` 判别，结算统一走一处。可减少一类"哪条路径负责结算"的分叉缺陷。
4. **Cordis runtime invariant 插件整体摘除**（`f028f25667d`，约 25 包的 `invariant.ts` 全删，改为普通回归测试）。**建议**：光明侧 `不变量登记.light` / `任务不变式.light` 是自有体系，**不跟随删除**；但应吸收其动机——"只被不变量覆盖的路径补成普通用例"，避免不变量成为唯一覆盖。

### 6.2 应当跟进的九条

5. 工具注册从"服务侧监听"改为"preset 行声明"（schedule 迁包）：能力可用性由组合声明（`toolFilter.deny` / `ctx.tools.restrict()`）而非服务存在性推断；lightharness 的 `预设挂载过滤.light` / `能力槽登记.light` 已有同构概念，建议按此形态落 §5-13。
6. 浏览器信任栅栏与身份认证分离：栅栏只回答"这个 Host 是否被允许"（防重绑定），不建立身份；认证另走一条。建议在 `web服务器.light` 明确这两层边界。
7. 凭据优先级翻转后，**写入语义**也要跟着变：托管存储是唯一可写层，环境变量与 `.env` 只读回退。建议 `凭据链.light` 显式区分"可写层"与"只读层"。
8. 模型列表的"不可用条目不隐藏"：条目即使缺能力也要保留 id/name/requirement，让 UI 能解释"为什么这个模型不能用"。建议 `模型目录.light` 采用同款结构（可用性 + 原因，而非过滤掉）。
9. 结算消息面向模型的可读性：`settlementSummary` 新增 `continuable` 参数、`structured`/`diagnostic` 两段拼接。建议 `子代理续传.light` 的结算文案按"能否继续"分支。
10. 令牌计量的 plan/commit 两段式：任何可失败的计量步骤先只读试算，全部通过才提交，保证"同一畸形事件每次重试表现一致"。建议推广到 `令牌计量.light` 的所有状态更新。
11. Typert Remote 懒装配（`remote-info.ts`）：生成定义不构造解析器，首次访问才建索引，schema 与 JSON Schema 投影按需缓存。建议在 `typert协议.light` 登记此惰性策略。
12. 目录 schema 版本化（`catalog.ts` v0/v1/v2 + `stateVersion` 单调递增）：建议 `包清单.light` / 插件清单采用同款版本门。
13. 决策笔记体系（`.agents/notes/{implemented,proposed,rejected}` 三态 + i18n 配对）：建议 lightharness 的 `docs/功能对标/` 引入 rejected 目录，避免已否决方案被反复提出。

### 6.3 仅登记不行动的五条

15. 错误跨边界按 `name` 比较（弃 instanceof，改 duck-typing）。

### 6.4 拒绝的五条
