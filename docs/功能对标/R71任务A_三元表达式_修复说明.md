## 二、语法口径（最终定稿）

```光明
# 形式1（推荐，任务书口径）：前缀式，则/那么 均可
设 结果 为 如果 x > 5 则 "大" 否则 "小"
设 结果 为 如果 x > 5 那么 "大" 否则 "小"

# 后置式（延续既有能力，与形式1等价）
设 结果 为 "大" 如果 x > 5 否则 "小"

# 缺省否则分支 → 空（None）
设 结果 为 如果 x > 100 则 "大"

# 生成物（两后端一致）：
#   (值1 if 条件 else 值2) / (值1 if 条件 else None)
```

## 三、修复前实测缺陷（本次消灭）

探针逐条实测（修复前），三元本体已可用，但存在两个**连带缺口**：

### 缺陷 1：三元分支吞逗号（列表/字典/调用参数场景）

- 复现：`设 e3 为 [如果 x > 5 则 1 否则 2, 99]` → 列表长度 1，`99` 被吞进否则分支。
- 根因：`parser_expr.py` 中前缀/后置三元的分支操作数走 `_parse_expr()`，其中的
  COMMA 分支是「因果链（Pipeline）」语法——三元分支把元素分隔逗号当因果链吞掉。
  `_parse_lambda`（parser_expr.py 内联三元处）的既有注释已记录同类结论：
  「不用 _parse_expr 因为后者会吃逗号（因果链）」。
- 连带炸点：`f(如果 c 则 1 否则 2, 3)` 丢参；字典值内三元同理。

### 缺陷 2：返回语句三元静默失效（任务书实现要点 5 的语句/表达式区分）

- 复现：`段落 f 接收 n: 返回 如果 n > 5 则 "大数" 否则 "小数"` → 调用返回 **None**。
- 根因：`parser_stmt.py` `_parse_return_stmt` 把 `如果` 列入语句关键字 →
  生成裸 `return` + 独立 if/else 语句（codegen 实证），静默丢返回值。
- 这正是任务书要点 5 要求的区分：语句位置 `如果` 后跟冒号+块体，表达式位置
  后跟条件+`则/那么`。

## 四、修复落点（light-merge/src/）

1. **parser_expr.py**
   - 后置三元延续从 `_parse_expr` 抽为 `_parse_postfix_ternary_cont(left)`（可复用，行为不变）。
   - 新增 `_parse_ternary_operand()`：逻辑表达式 + 可选后置三元延续，**不吞逗号/箭头**。
   - 前缀三元（`_parse_primary` 内）条件/则分支/否则分支全部改走 `_parse_ternary_operand`。
   - 后置三元 else 分支（原 `_parse_expr`）改走 `_parse_ternary_operand`（嵌套后置式保留）。
2. **parser_stmt.py**（`_parse_return_stmt`）
   - `如果/若` 增加三元形式前瞻：向后扫到行尾/冒号，先见 `则/那么` 即视为三元表达式，
     否则维持语句关键字判定（语句位置 `如果` 行为不变）。
   - 后置三元 else 分支改 `_parse_ternary_operand`；多值返回逗号检查从 elif 链改为
     独立步骤——`返回 1 如果 c 否则 2, 3` 三元后仍可多值。
3. **lexer.py**（`?` 报错文案）
   - `?` 永不支持口径不变，报错补指路：「若要写三元表达式，请用
     『如果 条件 则 值1 否则 值2』」。

## 五、形式2（`?:`）决策说明

任务书允许「二选一或都支持」，本任务交付形式1，形式2 不收录，依据：

- `lexer.py` A2-7 既有决策（有注释、有报错口径、记于移交清单与语法文档）：
  **`?` 永不支持**——它要与可空类型等未来语法抢词法位，且 `可空 X` 中文前缀式已走通；
- 引入 `?:` 属于推翻既定口径的语义决策，超出本任务「新增不破坏」的硬约束边界（6.4）；
- 已把开发者体验补齐：写 `?:` 会得到指路报错，明确导向形式1 写法。
