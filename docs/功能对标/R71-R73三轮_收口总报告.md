## 三、本轮收口新增修复（R71-R73 记账缺口，2 处）

三轮开发期间遗留了 **2 处门禁记账缺口**——都不是语法实现问题，而是「新模块/新搬迁
未同步登记」，导致两条 CI 门禁在本轮收口时判红。本轮一并修复：

### 3.1 地板门禁红（`floor_bootstrap.py`）

**红因**（9 处）：R72-E 为落地 L-159 在 `stdlib/内置核心判型.light` 第 47 行插入
`段落 是字节`，其后 8 个判型段落整体下移 5 行，而 `任务书/自举地板清单.json` 里
这 8 条的 `证据行` 仍指向旧行号（窗口 ±2 行找不到定义行）；同时 `是字节` 本身
未登记，撞上「builtins.py 里有、清单里没有（防腐烂）」。

**修复**：
1. 8 处证据行重定位（`是空` 46→51、`是字母` 50→55、`是数字` 54→59、`是空白` 58→63、
   `是布尔` 62→67、`是函数` 66→71、`是数值` 71→76、`是负零` 79→84）。
2. 登记 `是字节` 为 `has_light_impl`（真身 `stdlib/内置核心判型.light:47`，
   builtins.py 仅一行转发），插在 `是字典` 之后保持判型族聚簇。
   —— 该条目**沿用 R71-E/R72-E 既有搬迁口径**（真身纯光明 + Python 侧惰性转发），
   不改变任何代码行为，故不构成 §6.4 兼容性风险。

**结果**：清单 156 → 157 条，地板自举率 **70.21% → 70.53%（67/95）**，
基线已在合并点刷新。`tests/unit/test_地板搬迁_判型_S2.py` **361 passed**
（含 `是字节` 与 Python 原版逐条差分）。

### 3.2 原生产品门禁红（`native_product.py`）

**红因**：R72-E 新建的 `stdlib/字节缓冲.light` 未登记进 `任务书/原生腿产品清单.json`
模块表，撞上「stdlib 里有、模块表没登记的 .light（防腐烂）」。

**修复**：真编译实测取证后如实登记为 **不可编译**：
```
python -m cli.light compile stdlib/字节缓冲.light --backend llvm-typed
→ 原生（llvm-typed）编译错误: 未定义的段落：_light_bytes_split
```
阻断原因写明：原生后端缺运行期 helper `_light_bytes_split`（R72-E 为绕开
「bytes 字面量后跟 `.方法`」的 parser 限制，在 `src/code_generator.py` 注入的运行期
helper，与 `_light_get`/`_light_attr_get` 同层）。

**结果**：模块表 114 → 115 条，分母扩大使可编译比例 22.81% → **22.61%**
（分子 26 不变；未实测 0、坏路径 0、矩阵未实测 4 均未增）。基线已在合并点刷新，
门禁自校验通过。

> **口径说明**：分母扩大导致比例数值下降，是「新增模块全部登记」的必然结果，
> 不是可编译能力退步。门禁对「分母缩小虚涨比例」有专门红项（`module_total` 只升不降），
> 此处方向相反且已按门禁文档要求在合并点重建基线。
