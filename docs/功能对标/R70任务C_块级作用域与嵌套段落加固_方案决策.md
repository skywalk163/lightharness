# R70 任务 C：块级作用域与嵌套段落加固 — 方案决策文档

> **任务**：光明语言专项升级 R70 批次 任务 C
> **决策日期**：2026-09-19
> **决策结论**：采用 **方案 C（嵌套段落加固）**，块级作用域留待后续批次

---

## 1. 背景

光明语言当前变量作用域为**函数级**（类似 Python），`如果`/`遍历`/`当` 等块内定义的变量会泄漏到块外。L-078 已实现命名嵌套段落（函数级嵌套）+ `外层`(nonlocal) 标量捕获，6 场景测试全绿。

任务 C 要求在"块级作用域"与"嵌套段落加固"之间做出方案选择并落地。

---

## 2. 三个候选方案

### 方案 A：`设` = 块级声明，`为` = 赋值

- **内容**：将 `设 X 为 Y` 改为块级声明（类似 JS `let`），`X 为 Y` 改为赋值（沿作用域链向上查找）
- **优点**：语义清晰，与主流语言对齐
- **缺点**：
  - **破坏性极大**：现有大量代码依赖"变量泄漏"行为（函数级作用域），直接改为块级作用域会破坏全量回归
  - `设` 在块内的用法需全部审计迁移
  - 编译器需做完整的作用域分析，改动面覆盖解析器 + 代码生成 + 语义分析
- **结论**：**不可行**，全量回归零破坏是硬约束

### 方案 B：新增 `令` 作为块级声明关键字

- **内容**：`令 X 为 Y` 在当前块内声明变量，作用域限于当前块；`设` 保持函数级声明（向后兼容）
- **现状调查**：
  - `令` 在解析器中已被定义为 **C 风格变量声明**（`令 name = expr`），生成与 `设 name 为 expr` 相同的 VarDecl AST 节点
  - 经全仓扫描，`令` 在 lightharness 和 light-merge 的 `.light` 源码中**实际使用量为 0**
  - 因此理论上可以将 `令` 的语义从"C风格声明"改为"块级声明"，不破坏现有代码
- **Python 后端实现难点**：
  - Python 本身是函数级作用域，无原生块级作用域
  - 模拟方式一：**变量名 mangling**（块内变量名加唯一后缀，如 `_L1_x`），块外不可访问。但需要在代码生成器中维护作用域栈，且表达式生成时需做变量名重映射，与闭包捕获交互复杂
  - 模拟方式二：**`del` 语句**（块结束时 `del` 块内变量）。但条件分支中变量可能未定义就 `del`，且 for 循环变量处理复杂
  - 模拟方式三：**立即执行函数包装**（把块体包装成嵌套函数并立即调用）。但会改变 `return`/`break`/`continue` 的控制流语义，不可行
- **风险评估**：
  - 变量名 mangling 方案需改动代码生成器的表达式生成路径，与 L-078 闭包捕获、任务 A 匿名函数、任务 B async/await 均有交互面
  - R70 批次 A/B/C/D 并行开发，方案 B 的作用域栈改动可能与其他任务产生合并冲突
  - 测试覆盖难度高：块级作用域与闭包、循环、异常处理的组合场景繁多
- **结论**：**本批次不实施**，留待后续批次在 A/B 合入后、无并行冲突时单独实施

### 方案 C：嵌套段落加固（本批次采用）

- **内容**：不引入块级作用域，专注于加固 L-078 嵌套段落的深度和健壮性
- **具体工作**：
  1. 编写 `examples/test_nested_deep.light`，验证 ≥3 层嵌套段落
  2. 验证多层闭包捕获（跨 ≥2 层的变量读取和修改）
  3. 验证闭包变量生命周期（外层函数返回后，闭包仍持有捕获变量）
  4. 验证递归嵌套（嵌套段落中调用自身或外层段落）
  5. 验证嵌套段落与 `外层`(nonlocal) 的多层交互
  6. 全量回归确保零破坏
- **优点**：
  - **零风险**：不改动编译器代码，仅新增测试用例，全量回归必然通过
  - 加固 L-078 的边界场景，发现潜在问题
  - 为未来块级作用域实施提供测试基线
- **缺点**：
  - 不引入新语言特性，块级作用域问题留待后续
- **结论**：**本批次采用**

---

## 3. 决策理由

1. **全量回归零破坏是硬约束**：方案 A 直接违反此约束，方案 B 有较高回归风险
2. **R70 批次并行开发**：A/B/C/D 四个任务并行，方案 B 的作用域栈改动与任务 A（匿名函数闭包）、任务 B（async/await）有直接交互面，合并冲突风险高
3. **`令` 关键字已被占用**：虽然实际使用量为 0，但将其从"C风格声明"改为"块级声明"属于语义变更，需谨慎评估
4. **Python 后端限制**：模拟块级作用域需要变量名 mangling，实现复杂度中等，且与闭包捕获交互复杂，适合在无并行任务的独立批次中实施
5. **嵌套段落加固有实际价值**：L-078 虽已实现，但深度嵌套（≥3层）、跨多层闭包修改、递归嵌套等边界场景尚未系统验证

## 4. 块级作用域后续实施建议（留待 R71+）

### 4.1 推荐实施路径

1. **前置条件**：任务 A（匿名函数）、任务 B（async/await）已合入，无并行冲突
2. **关键字选择**：将 `令` 从"C风格声明"改为"块级声明"（实际使用量为 0，无破坏）
3. **实现方式**：变量名 mangling
   - 代码生成器维护 `self._scope_stack = [{}]`
   - 进入 `如果`/`遍历`/`当`/`尝试` 块时 push 新作用域
   - `令 X 为 V` 时生成唯一名称 `_L{depth}_{unique}_{X}`，注册到当前作用域
   - 表达式生成时，变量名查找从内到外搜索作用域栈，找到则用 mangled 名
   - 离开块时 pop 作用域
4. **与闭包的交互**：
   - 闭包捕获块内变量时，mangled 名需传递到嵌套函数
   - `外层`(nonlocal) 声明需识别 mangled 名
5. **测试覆盖**：
   - 块级作用域基础（if/for/while/try）
   - 块内外同名变量互不干扰
   - 闭包捕获块内变量
   - 块级作用域与 `设`（函数级）共存
   - 异常处理中的块级作用域

### 4.2 风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 变量名 mangling 与闭包捕获交互复杂 | 先实现基础块级作用域，再逐步支持闭包捕获块内变量 |
| 与任务 A/B 的合并冲突 | 在 A/B 合入后单独批次实施 |
| 性能影响（作用域栈查找） | 作用域深度通常 ≤5，查找开销可忽略 |
| 错误信息可读性 | mangled 名需在错误信息中还原为原始变量名 |

### 6.4 发现的语法限制（非缺陷，记录备查）

在编写测试用例过程中发现以下语法限制，均有绕法，不影响本任务交付：

1. **匿名闭包在括号内不支持块体**：`(段落 接收 x: 段落 内部: ...)(21)` 形式的 IIFE 无法解析。绕法：先 `设` 为变量再调用，或使用单行表达式体。
2. **递归调用在复合表达式中需分步**：`返回 n * 阶乘(n - 1)` 形式的递归调用可能被解析器误判。绕法：先 `设 递归结果 为 阶乘(n - 1)` 再 `返回 n * 递归结果`。

以上限制建议在后续批次（任务D或R71）评估是否修复。
