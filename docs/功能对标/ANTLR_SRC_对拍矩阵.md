## 三、附带发现（不在本批修，供后续立账参考）

### S1 · SRC 判型族在「无 stdlib 祖先目录」下退化为 `属性错误`（环境依赖，非 SRC 逻辑缺陷）

- **现象**：同一份 `lp019_判型族.light`，cwd 在 `lightharness/` 或 `light-merge/` 下 SRC rc=0 全绿；
  cwd 换成 `probes/`（其祖先链上**没有** `stdlib/` 目录）或 `/tmp/nostd` 下 → SRC rc=1。
- **机制**（已逐环验证）：
  1. 生成码里 `_light_stdlib` 依次试 `<文件目录>/stdlib` → `<文件目录>/../stdlib` →
     `cwd/stdlib` → `<文件目录>/../../stdlib`；**全落空即 `_light_stdlib = None`**；
  2. `_light_stdlib is None` ⇒ `importlib` 分支 `raise ImportError()` ⇒ 落到
     **`except` 降级桩** `types.ModuleType('_light_builtin')`；
  3. 降级桩**只定义了 `是数值`**（`('是数值', lambda v: isinstance(v,(int,float)) and not isinstance(v,bool))`），
     **没有定义 `是数字`**；
  4. 而 `builtin_map` 里 `是数字符` → `_light_builtin.是数字`
     ⇒ `是数字(7)`（映射到 `是数值`）能过，**`是数字符("7")` 必然 `AttributeError`**。
- **旁证**：`light-merge/stdlib/builtins.py` **同时**有 `是数值` 与 `是数字`（故 cwd 正确时全绿）；
  而 `lightharness/stdlib/builtins.py` 与 `light-merge/bootstrap/release/stdlib/builtins.py`
  **只有 `是数字`、没有 `是数值`** —— 三份 builtins 副本判型族覆盖不一致，是该脆弱面的来源。
- **定性**：**不是 SRC codegen 的逻辑错误**，是「stdlib 解析失败后降级桩覆盖不全」的**环境依赖**。
- **建议处置**（本批不做）：
  ① 降级桩补齐 `是数字`（与 `是数值` 并列）⇒ 最小、最对症；
  ② 三份 `builtins.py` 判型族覆盖对齐（`lightharness/stdlib` 与 `bootstrap/release/stdlib` 补 `是数值`）；
  ③ 探针跑法固化：cwd 必须在 `lightharness/` 或 `light-merge/` 内，否则结论不可信。
- **对本矩阵的影响**：行 3 的 SRC 单元格标 **⚠️ 条件通过** 而非 ✅，避免下轮误判成「SRC 已修」。

## 四、维护规程

1. **触发**：任何一次两后端行为不一致的实测（含修完复验）→ 本表加/改一行。
2. **证据要求**：每行必须能落到**可复跑探针**；只写结论不写探针的行不予采信。
3. **跑法铁律**：cwd 固定 `lightharness/` 或 `light-merge/`（见 §三·S1-③），退出码用
   `out=$(cmd 2>&1); rc=$?` 取，**不要用 `| tail` / `| head` 吞退出码**（`$?` 会变成管道末端命令的）。
4. **两处口径不许混淆**：
   - 「SRC 错」≠「ANTLR 对」——修哪边取决于**哪边是权威**（LP-D-018/019 都是 **ANTLR 为准**，SRC/ANTLR 各自补）；
   - 「两后端一致」≠「对」——可能一起错（那是 `行为差异清单.md` 或语言层限制的领地）。
5. **状态词统一**：`待修` / `本批修（在途）` / `已修（复验绿）` / `条件通过（见 S1）`，不用自由描述。
