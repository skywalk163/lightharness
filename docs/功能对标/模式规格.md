# 模式规格：6 模式 × 7 小节契约

本文登记 lightharness 里 6 个 agent 模式的**可执行契约**：四个组合型（`topdown` / `bottomup` /
`brainstorm` / `lazy`），两个行为型（`goal` / `plan`）。

为什么需要这份文档：这些模式在 DSH 里是 Agent Preset 的规格化产物，真正的差异不在工具清单，
而在「**控制流向 / 人机介入点 / 终止条件**」这三维。代码只能告诉你「这个模式挂了哪些工具」，
三维契约只存在于提示文案与决策层的判据里，不落文档下一个人只能靠读代码猜。

口径三条，全文遵守：

1. 只写**已经落地为判据**的内容。判据 = 代码里能被断言的东西（提示段落原文、组合行表的增删、
   决策函数的返回码、开关默认值），不写修辞。
2. 落点写成可查的名字：文件 + 段落名（行号随改动漂移，只作为当前提交的坐标）。
3. 已随 T-0407 落地的写「已接线（T-0407，main 41ae48a）」；仍未落地的写「仍未接线（卡 T-0420 / T-0419）」，不写成已生效。

## 0. 模式总表

| 模式 id | 类型 | 中文名 | 预设 order | 是否进 `预设清单()` | 主要落点 |
|---|---|---|---|---|---|
| `topdown` | 组合型 | 自上而下 | 5 | 是 | `src/预设组合.light` §2.5 / `src/预设.light` §八 |
| `bottomup` | 组合型 | 自下而上 | 6 | 是 | `src/预设组合.light` §2.5 / `src/预设.light` §八 |
| `brainstorm` | 组合型 | 头脑风暴 | 7 | 是 | `src/预设组合.light` §2.5 / `src/预设.light` §八 |
| `lazy` | 组合型 | 懒人 | 8 | 是 | `src/预设组合.light` §2.5 / `src/预设.light` §八 |
| `goal` | 行为型 | 目标模式 | 不适用 | **否** | `src/目标续跑.light` + `src/目标轮驱动.light`（复刻件）+ `src/目标工具.light` |
| `plan` | 行为型 | 计划模式 | 不适用 | **否** | `src/计划模式.light`（复刻件）+ `src/预设组合.light` §1 `规划组行` |

类型差别是硬差别，不是命名习惯：

- **组合型**是预设（preset）—— 切换预设 = 换一整份插件行表；`组合清单()` 的键就是它们，
  `预设清单()` / `是已知预设()` / 设置页下拉都从这里派生，加一个组合型模式只改 `组合清单()`。
- **行为型**不是预设 id，不进 `组合清单()`、不进 `预设清单()`，不出现在设置页预设下拉里。
  它们是会话级的行为开关：`goal` 靠目标台账 + 轮次驱动续跑，`plan` 靠一个 `plan/mode` 折叠位
  改变「做还是只出计划」，工具集不动。

## 0.1 分层：Agent 模式 / 工作方法（T-0439）

8 个预设 id 原本平铺在同一张清单里，混了两类东西。T-0439 起数据层给每个组合条目加 `类别`：

| 类别 | 含义 | 成员 | 对齐对象 |
|---|---|---|---|
| `agent` | Agent 模式：差异在「挂哪些工具」 | `standard` / `cordis`（创造）/ `ptc` / `minimal` | DSH `packages/bundle/web-app/presets/*.patch.yml` |
| `method` | 工作方法：差异在「怎么推进」 | `topdown` / `bottomup` / `brainstorm` / `lazy` | trae agent 的 spec / plan / goal 一类工作流 |

口径（写死，避免实现漂移）：

- `组合清单()` 仍是唯一真相；`预设类别()` 从条目读 `类别`，不另抄清单一。
- `预设清单()` 默认仍返回 8 项；`预设清单("agent")` 返回 4 项、`预设清单("method")` 返回 4 项，
  未知类别返回空列表（查询语义，不抛错）。
- `预设分组()` 返回 `{"agent": [...], "method": [...]}`（各自按 `order` 升序）。
- 呈现：主输入区下拉、新会话面板、设置页「Agent预设」都按「Agent 模式 / 工作方法」两组渲染；
  **值仍是单个预设 id**，切换仍是整份行表替换。
- 刻意**不做**「模式 × 方法」正交组合：那会产生 8×4 的组合面，需要新的会话字段与组合行表
  求并集规则，另开卡再谈。

## 0.2 轮数预算（T-0439）

| 预算 | 位置 | 旧值 | 新值 | 覆盖方式 | 参考口径 |
|---|---|---|---|---|---|
| 单轮步数 | `src/步数上限.light` `步数缺省`（唯一真相；`src/代理.light` 属性缺省也从这里取） | 25 | 96 | 请求体 `最大步数` > 环境 `HARNESS_MAX_STEPS`（1..1000） | 一步 = 一次模型请求 + 同批工具调用 |
| 目标续跑轮数 | `src/目标续跑.light` `续默认最大轮数` | 8 | 64 | 目标台账 `maxGoalRounds` | DSH `tool-ralph` 的 `maxRounds` 默认 256（`packages/experimental/tool-ralph/src/index.ts:35`） |
| 纯逻辑复刻轮次 | `src/代理循环.light` `默认最大轮次` | 3 | 不动 | 仅单测使用 | 对齐上游 agent-loop 的最小复刻，不是运行时预算 |

为什么 64 而不是 256：DSH 的 ralph 一轮只推进一次「工具轮」，本仓一轮 = 一整轮对话
（模型请求 + 工具批 + 收口），单位成本高一个量级；同时 `续默认无进展阈值 = 2` 先生效，
空转两轮就停，不会把 64 轮烧满。需要更长跑的任务按单目标 `maxGoalRounds` 显式放宽。

## 模式 1 · topdown（自上而下）

### 触发方式

- **显式切预设**：会话 / 设置里把模式选成 `topdown`（`造预设元数据("topdown", "自上而下", …)`，
  `src/设置页.light:90`）。切完 `预设清单()` 里 order 5 组合生效。
- **prompt 意图路由**：用户给出的是「有依赖关系的多产物任务」（跨文件重构、改一套架构、
  要交付一份方案要点）时按 `topdown` 处理。路由判据 = 任务能否拆出「叶子 → 上层」的依赖边；
  能拆出依赖边就不该按单点改动走。路由的执行为 `总入口` 的模式选择（接线已由 T-0407 落地（main 41ae48a））。

### 进入条件

- 适合：产物之间**有依赖顺序**，且「计划本身」要有交付价值；预估要动 ≥ 3 个文件或跨 ≥ 2 个模块。
- 不该用：单点小改（1–2 个文件、无依赖边，直接用 `standard`）；纯方案讨论（该用 `brainstorm`）；
  需求本身还没定（先讨论或走 `lazy` 的方案层检索，不要在树里塞假设节点）。

### 控制流向

- 决策从**顶层**发起：先出计划树（节点 = 目标 / 依赖 / 预估依据），再由上向下传递。
- **有中央规划器**：计划树本身就是规划器。执行按依赖顺序推进**叶子节点**，叶子内不再重规划。
- 子 Agent 只在叶子内执行，不自行改树；改树只能由顶层显式改。
- 每完成一个节点，回报该节点的产出 + 下一批可动节点（可动性由依赖边算，不靠感觉）。

### 人机介入点

- **必须介入（硬点）**：计划树首次成形时，整棵树提交给用户确认。被拒 → 改树后重新提交；
  **不允许绕开确认直接开写**。
- **可以介入**：执行中途用户主动插话，插话按会话队列的「插话」语义进入，不改已确认的树；
  要改树必须重新走一次整树确认。
- **一律不打断**：叶子内部执行不逐节点请示；节点失败先尝试回退到上层节点换路，换不了才上报。

### 输出形态

- 一等产物是**计划树**：节点三件事（目标 / 依赖 / 预估依据），树不是「随手可改口的草稿」。
- 过程产物是**节点回报**：完成节点 → 产出 + 下一批可动节点。
- 树变更留痕：显式改树 + 说明为什么改，不允许「边做边在心里换方案」。

### 终止条件

- **正常终止**：计划树叶子全部完成。
- **硬终止**：用户拒绝计划且不接受改树；某节点失败且无法回退到上层节点换路。
- **预算上限**：`topdown` 保留 `tool-goal`（见实现要点），所以续跑预算同样生效 ——
  `续默认最大轮数 = 8`、`续默认无进展阈值 = 2`（`src/目标续跑.light:33-34`），
  命中即 `round-limit` / `no-progress` 停止。

### 实现要点

- 数据层：`src/预设组合.light` §2.5 `自上而下组合行表()`（当前 :222）—— 以 `标准组合行表()`
  为基底**不删不加**（全 4 工具 + `tool-goal`），差异全在提示：计划树是一等产物。
- 提示契约：`src/预设.light` §八 `自上而下提示()`（当前 :467）由 `模式系统提示("topdown")` 分发。
- 终止清单：`模式终止条件("topdown")` 返回
  `["计划树叶子全部完成", "用户拒绝计划且不接受改树", "某节点失败且无法回退"]`（当前 :561）。
- 设置页文案：`src/设置页.light` `帮助正文("topdown", …)`（当前 :119）。
- 刻意边界：
  - 提示**注射点不在** `预设.light` —— 它只产纯文本；`模式系统提示(预设标识)` 塞进
    `选项["系统提示文本"]` 的接线已由 T-0407 落地（main 41ae48a）。
  - 不引入任何「自动改树」逻辑：树只能整棵换，不能增量漂移。
  - 叶子执行**不自动** fork 子 Agent：要不要并行由顶层的委派组决定，不由模式决定。

## 模式 2 · bottomup（自下而上）

### 触发方式

- **显式切预设**：模式选成 `bottomup`（`造预设元数据("bottomup", "自下而上", …)`，
  `src/设置页.light:92`），order 6 组合生效。
- **prompt 意图路由**：用户给的是「清单式、可独立推进的活」（一批同类小修、逐文件套模板、
  跑一批互不相干的用例）时按 `bottomup` 处理。路由判据 = 单元之间**没有依赖边**、
  且每个单元都能独立验收。

### 进入条件

- 适合：任务能切成互不依赖的原子单元，且「全局一致」不是验收前提；单元粒度 = 一个文件 /
  一处调用 / 一条断言。
- 不该用：需要前后依赖推进的重构（用 `topdown`）；需要用户逐步确认的任务（本模式不请求确认）；
  一致性优先的改动（单元之间的交叉修改必须先串行化）。

### 控制流向

- **没有中央规划器**。流向是「扫单元 → 领一个 → 做完 → 交回结果 → 再领下一个」，
  单元之间不互相等待，也不为「全局一致」先搭一层大计划。
- 进度 = 单元清单的完成度，**用单元清单代替目标树**：数据层不提供 `tool-goal`。
- **硬约束（判据，不是修辞）**：去重与冲突检测必须放在**协调器**（顶层会话），
  Worker 之间**不能互相看到输出**，否则会退化成隐式集中协调 —— Worker 各自读别人的产出再
  互相让步，等价于一个没人管的规划器。
  - Worker 的可见输入只含它自己那个单元；交回的是「结果 + 我碰了哪些单元」。
  - 协调器按单元标识去重（同一文件 / 同一调用点只计一次），交叉改动由协调器串行化，
    冲突不得由 Worker 私下协商解决。

### 人机介入点

- **不主动介入**：本模式**不请求确认**（数据层 `tool-ask-user` 被删，见实现要点）。
  遇到歧义按最小改动选一个默认值继续，并把默认值写进该单元的结果里，让人事后能看出
  你替他做了什么决定。
- **可以介入**：用户主动插话按会话队列的「插话」语义处理 —— 插话成为**新单元**挂到清单尾部，
  不打断正在做的单元。
- **一律不打断**：单元之间不逐单元请示；只有不可逆操作仍受权限闸门约束。

### 输出形态

- **结果集合**：单元清单 + 每个单元的结果 + 每个单元的默认值记录（不是计划树，也不是想法池）。
- 单元清单是这一模式的唯一进度视图：没有目标台账，所以没有 `phase` 可标。

### 终止条件

- **正常终止**：所有已发现单元处理完。
- **硬终止**：连续两轮以上没有新的有效产出（单元清单不再新增 / 完成度不再推进）。
- **预算上限**：到达总轮次 / 成本上限。注意本模式**没有** `tool-goal`，所以不套用
  `续默认最大轮数 = 8` 那套续跑预算，预算由会话级轮次 / 成本门判定。

### 实现要点

- 数据层：`src/预设组合.light` §2.5 `自下而上组合行表()`（当前 :228）——
  `删表 = ["tool-goal", "tool-ask-user"]`，其余以 `标准组合行表()` 为基底。
  删 `tool-goal` 是「用单元清单代替目标树」的数据层投影；删 `tool-ask-user` 是
  「不主动请求确认」的投影。
- 提示契约：`src/预设.light` §八 `自下而上提示()`（当前 :484）。
- 终止清单：`模式终止条件("bottomup")` 返回
  `["所有已发现单元处理完", "连续两轮以上无新有效产出", "到达总轮次/成本上限"]`（当前 :563）。
- 设置页文案：`src/设置页.light` `帮助正文("bottomup", …)`（当前 :124）。
- 刻意边界：
  - **单元清单不落独立模块**：它由顶层会话循环持有（接线已由 T-0407 落地（main 41ae48a））。本仓不新建一个
    「单元调度器」类 —— 协调器就是顶层会话，重复造调度器等于又造一个中央规划器。
  - Worker 上下文必须隔离：派 Worker 只走子代理的隔离上下文，不允许把别人的输出拼进它的
    输入当作「上下文参考」。
  - 去重只在协调器做；Worker 侧不提供「查重」接口 —— 一旦 Worker 能查重，它就开始看别人的活了。

## 模式 3 · brainstorm（头脑风暴）

### 触发方式

- **显式切预设**：模式选成 `brainstorm`（`造预设元数据("brainstorm", "头脑风暴", …)`，
  `src/设置页.light:94`），order 7 组合生效。
- **prompt 意图路由**：用户要的是「先讨论方案、不要动代码」（「先给几个思路」「方案上还有哪些可能」
  「这条路和那条路比一下」）时按 `brainstorm` 处理。路由判据 = 用户要的是**取舍依据**而不是**改动**。

### 进入条件

- 适合：方案探索、路线取舍、风险评估；需要铺开可能性再排序的场景。
- 不该用：需要落地的改动（本模式**只挂只读工具**，写不了也不该假装写过）；需要跑命令验证的活
  （没有 `tool-bash` / `tool-pwsh`）；已经有明确实现路径的任务（直接做，别再走一轮讨论）。

### 控制流向

- 两阶段 + 中间一道**硬闸**：发散（不评判）→ 硬闸（人）→ 收敛（Steelman + Devil's Advocate + 排序）。
- **没有中央规划器**：阶段切换由硬闸推进，不由 Agent 自行推进 —— Agent 不得自问自答地把闸门
  推过去。
- **硬约束（判据，不是修辞）**：发散阶段**禁止出现**「这个想法好不好」的判断 ——
  禁打分、禁说「不可行」、禁提前收敛。每条想法只写「一句主张 + 一句为什么可能成立」。
- 收敛阶段至少要有两个角色：**Steelman**（这个方案最强的版本）与 **Devil's Advocate**
  （最致命的反驳）；两角色都出完再排序，并说明排序依据。

### 人机介入点

- **必须介入（硬点）**：发散结束必须显式停下，把想法列成清单交给用户，**用户选完**才进收敛。
- **可以介入**：收敛阶段用户可随时补充约束（新约束按新条目进池，不改已排序的名次口径）。
- **一律不打断**：发散阶段内部逐条产出不请示、不打断；唯一例外是用户喊停。

### 输出形态

- **分层想法池**：
  - 发散层：想法清单，每条 = 一句主张 + 一句为什么可能成立（无评分、无排序）。
  - 收敛层：留下的方案每条同时给 Steelman 与 Devil's Advocate，再出排序 + 排序依据。
- **「争议区」是刻意保留的**：排序里名次不稳、两角色结论相反的那批方案单列成争议区，
  **UI 层不得折叠** —— 折叠争议区等于把「还没想清楚」伪装成「已定论」。

### 终止条件

- **正常终止**：收敛阶段排序连续多轮稳定（名次不再变化）。
- **硬终止**：用户喊停（发散阶段喊停即结束；硬闸处拒绝进入收敛同样是硬终止，不回落到自问自答）。
- **预算上限**：发散阶段到达最大轮次即收口（`模式终止条件` 原文「发散：到最大轮次或用户喊停」）。

### 实现要点

- 数据层：`src/预设组合.light` §2.5 `头脑风暴组合行表()`（当前 :234）——
  `删表 = ["tool-bash", "tool-pwsh", "tool-goal", "delegation"]`，保留 `tool-fs` /
  `tool-fs-search` / 压缩 / 规划。
  删 `delegation` 是**纪律要求**：子 Agent 能绕过只读约束，所以整组 10 行一起删。
  删 `tool-goal` 是因为 goal 工具会推进改动。
- 提示契约：`src/预设.light` §八 `头脑风暴提示()`（当前 :501）。
- 终止清单：`模式终止条件("brainstorm")` 返回
  `["发散：到最大轮次或用户喊停", "收敛：排序连续多轮稳定"]`（当前 :565）。
- 设置页文案：`src/设置页.light` `帮助正文("brainstorm", …)`（当前 :129）。
- 只读边界（T-0419 已落装配层）：
  - `src/总入口.light` 的「工具名到叶子」已把「读文件」映到 `tool-fs-read`、「写文件」映到

## 模式 4 · lazy（懒人）

### 触发方式

- **显式切预设**：模式选成 `lazy`（`造预设元数据("lazy", "懒人", …)`，`src/设置页.light:96`），
  order 8 组合生效。
- **prompt 意图路由**：用户只描述**想要的结果**、不关心实现细节（「把这批空指针报错处理掉」
  「随便弄个能用的」），或明确说「别问我，你自己定」时按 `lazy` 处理。
  路由判据 = 用户给的是**意图**而不是**实现路径**，且可接受默认值。

### 进入条件

- 适合：目标清楚、实现路径开放、成本敏感、缺参数可由保守默认值兜住的任务。
- 不该用：需要精确规格 / 合规审查 / 不可逆操作密集（必须逐步确认）的任务；需求本身未定
  （先 `brainstorm`，不要在「懒」的名义下拍脑袋定需求）。

### 控制流向

- **决策阶梯**自顶向下让步，能用上一级就不用下一级：
  1) 不做（这件事真的需要做吗）；2) 现成的开源项目或服务；3) 现成的开源库；
  4) 已有依赖或标准库；5) 一行命令 / 一行代码；6) 才写新代码。
- **硬约束（判据，不是修辞）**：进入第 6 级（代码层）之前必须留下**「方案层已穷尽」**的依据 ——
  候选项目名 + 排除理由，排除理由限定在三类：**license** / **维护停滞** / **集成成本高于自写**。
  只写「找过了，没有合适的」不算依据。
- **成本闸**：预估自写行数 **< 20 行**时**不触发**开源检索 —— 为了少写几行反而先去搜一圈，
  净成本更高。判据在 `需开源检索(预估自写行数)`：非整数一律返回真（宁可搜），整数且 < 20 返回假。
  20 行以下虽不必先检索，但「为什么不用现成方案」仍要落在依据里（此时「规模只有 N 行、
  检索净成本更高」就是合法的排除理由）。

### 人机介入点

- **必须介入**：只在**不可逆操作**（删数据、对外发送、花钱）之前停下确认。
- **可以介入**：用户随时可插入新约束；插入按会话队列的「插话」语义，不打断当前动作。
- **一律不打断**：缺参数不追问 —— 选最保守的默认值继续，末尾附**默认决策日志**，
  逐条列出替用户定的默认值和理由。

### 输出形态

- **最小交付物**（最小必要产物，不是「顺手多做一点」）+ **默认决策日志** +
  动代码前的「方案层已穷尽」依据。
- 三者缺一不算交付：交付物证明做成了，默认决策日志证明替用户决定了什么，
  依据证明没有跳级。

### 终止条件

- **正常终止**：用户意图以最小必要产物被满足。
- **硬终止**：触碰不可逆操作的安全边界（停下等确认，确认前不继续）。
- **预算上限**：达到硬迭代上限。可调开关 `minimal_action`（最小必要行动）与 `no_ask`
  （最少交互自主跑）**默认都开**（`模式开关表("lazy")`）。

### 实现要点

- 数据层：`src/预设组合.light` §2.5 `懒人组合行表()`（当前 :240）——
  `删表 = ["tool-ask-user"]`，其余全保留（含 `tool-web`，检索能力靠它）。
  删 `tool-ask-user` 是「不追问细节」的投影。
- 提示契约：`src/预设.light` §八 `懒人提示()`（当前 :518）。
- 终止清单：`模式终止条件("lazy")` 返回
  `["用户意图以最小必要产物被满足", "触发不可逆操作安全边界", "达到硬迭代上限"]`（当前 :567）。
- 开关默认值：`模式开关表("lazy") → {"minimal_action": 真, "no_ask": 真}`（当前 :575）。
- 成本闸：`需开源检索(预估自写行数)`（当前 :582）—— 整数且 < 20 → 假，否则 → 真。
- 设置页文案：`src/设置页.light` `帮助正文("lazy", …)`（当前 :134）。
- 刻意边界：
  - 不自动联网：检索只经 `tool-web`，模式本身不发起网络访问。
  - 20 行阈值是**成本闸**不是质量门：不许拿「少于 20 行」去绕「方案层已穷尽」的依据。

## 模式 5 · goal（目标模式，行为型）

### 触发方式

- **显式触发**：会话带一个活跃目标（目标台账非空）+ 目标工具在场。工具名 `目标` / 别名 `goal`
  （`src/目标续跑.light:36-37`），声明行是 `标准组合行表()` 的 `command-goal` / `tool-goal`。
  `goal` **不是**预设 id，不进 `组合清单()`。
- **prompt 意图路由**：用户说「这个任务跑到底」「不用一轮一轮问我继续」、或任务明显需要多轮推进时
  按 `goal` 处理。路由判据 = 目标能否写成**一句话的验收条件**。接线已由 T-0407 落地（main 41ae48a）。

### 进入条件

- 适合：目标可写成一句话验收条件、需要多轮推进（一批测试逐个修、逐个清 lint、逐项过 checklist）。
- 不该用：目标不可判定完成（纯讨论、需求还在变）；需要用户每轮拍板（用 `topdown` 的整树确认）。
- 依赖关系：`goal` 需要预设挂载 `tool-goal`。当前挂载它的组合是 `standard` / `ptc` / `cordis` /
  `topdown` / `lazy`；`bottomup` 与 `brainstorm` 明确删了它，`minimal` 整份不含它 ——
  在这些预设下 `goal` 续跑**不可用**，这是数据层的硬事实，不是可选建议。

### 控制流向

- 一轮结束 → `续续跑决策(状态, 轮次结果)` → 三选一：
  - `续跑`：把决策里的 `提示文本` 作为**下一轮用户文本**再驱动一次（文案复用
    `目标轮驱动.渲染目标轮文本`，不另写一份）；
  - `完成`：目标 `phase == "complete"`，收工；
  - `停止`：带 `理由` 上报。
- 判定一律委托复刻件：轮次预算 / 相位 / 授权 → `目标轮驱动.推进一轮`；
  `max-tokens` / `aborted` → `目标轮驱动.轮次结束栅栏`（解除自动续作授权）。
  **本层不重造完成判定。**
- 每轮结束调 `续记账(状态, 轮次结果)` 写回台账，否则「轮次 / 连续无进展」不推进；
  目标变更（`revision` / `phase`）经 `续合并目标变更(状态, 变更表)` 写回。
- **无中央规划器**：goal 只负责「还没完成就再来一轮」，规划由当前预设的模式决定。

### 人机介入点

- **必须介入**：目标被标 `complete`（用户或模型任一可标）即结束，不再自动续；
  硬栅栏命中时把 `理由` 上报给人（`round-limit` / `no-progress` / `max-tokens` / `aborted` / …）。
- **可以介入**：用户随时可改目标（改台账 → `续合并目标变更` 吸收）。
- **一律不打断**：轮与轮之间**不做逐轮确认** —— 逐轮确认正是 `goal` 要消灭的东西。

### 输出形态

- 多轮轮次日志 + 目标台账（视图键 `phase` / `revision`）+ 每轮产出。
- 不是计划树，也不是结果集合：`goal` 的产物是「一个任务的多轮推进记录」。

### 终止条件

- **正常终止**：目标 `phase == "complete"`（决策码 `goal-complete`）。
- **硬终止**：`max-tokens` / `aborted`（轮次结束栅栏，解除自动续作授权）、`error` / `max-steps`、
  `no-goal`（没有活跃目标时不续）、`no-progress`（连续 2 轮 `revision` 未变，阈值 `续默认无进展阈值 = 2`）。
- **预算上限**：`续默认最大轮数 = 8`（`round-limit`，先于无进展判定）；另叠每轮 token 预算
  （压缩阈值），由压缩层负责。

### 实现要点

- 决策层：`src/目标续跑.light`（零 IO、零线程，不导入 代理 / web服务器 / 总入口）：
  `续建续跑状态` / `续记账` / `续续跑决策` / `续合并目标变更` / `续目标工具规格` / `续执行目标工具`。
  段落一律 `续` 前缀（依赖模块内联后防撞名）。
- 复刻件（**只 `导入` 复用，不改**）：`src/目标轮驱动.light`（`推进一轮` / `轮次结束栅栏` /
  `渲染目标轮文本` / `视图取` / `新轮次驱动状态`）与 `src/目标折叠.light`。
- 工具注册：`src/目标工具.light` 的 `注册目标工具(注册表)` / `目标工具处理(参数)`。
- 接线（T-0407）：外层 `当` 循环每轮结束后调 `续续跑决策`；动作为「续跑」就把提示文本当下一轮
  用户文本。本卡不改 `总入口` / `代理` / `web服务器`。
- 刻意边界：无活跃目标时**不自续**（`no-goal` 停止）；不自行造完成判定；不绕过权限闸门。

## 模式 6 · plan（计划模式，行为型）

### 触发方式

- **显式切换**：`/plan` 命令（事件 `command/run`，`data.name == "plan"`；`args == "off"` 退出，
  `args` 缺 / 空则不改状态）。命令跑成功且期望值与当前 `active` 不同时才落 `active`；
  未闭合轮次里发起的命令先挂 `pending`。`plan` **不是**预设 id —— 它是会话上的一个折叠位。
- **prompt 意图路由**：`plan` 生效期间，用户的**祈使句式改动请求**（「改掉这个 bug」「重构这段」）
  按「要计划、不要执行」处理。判据是 `plan-mode` 的 section 原文：
  「Imperative language to implement changes means plan the implementation, not execute it.」

### 进入条件

- 适合：改动面大、需要先评审方案（多文件重构、动热点文件、要用户预审路线）。
- 不该用：单点小改（直接做，别多一道闸）；纯方案讨论（用 `brainstorm`，那里才铺开可能性）。
- 前提：`plan` 只改「做还是只出计划」，**不动基础工具集** —— 任何挂载 `规划组行` 的预设下都存在；
  开启期间额外只多挂一个出口工具 `exit_plan_mode`（T-0420 落地）。

### 落地现状（T-0420 已接线）

- 入口：`src/web服务器.light` 的 `/plan` 前缀识别 + `处理计划命令`（忙 409；落
  `command/run` / `command/done` / `plan/mode`）；`/plan`、`/plan on` 开，`/plan off` 关。
- 出口：`src/计划工具.light` 定义 `exit_plan_mode` 规格与 fail-loud 校验（空 / 非字典 / 空白计划即报错；
  `title` 缺省取首个标题，再回「计划」）；工具只在 `active` 时由 `web服务器` 用本会话闭包注册，
  成功后落 `plan/mode(false)` + `plan/submitted{plan,title}`，`concludesTurn:true`。
- 投影：`src/计划模式.light` 的 `折叠计划状态` 折 `plan/mode` 与最后一次 `plan/submitted`，
  产出 `{active,pending,text,title}`；`GET /api/sessions/current`、`GET /api/sessions/:id` 带 `计划` 键。
- 提示：`src/预设组合.light` 的 `计划提示文本` 取 `规划组行` 中 `plan-mode` 的 section；
  `src/总入口.light` 把它作为系统提示的前置段注入（人格 + 默认契约仍在其后）。
- 拦截：`src/代理.light` 的计划模式拦写对 `exit_plan_mode` 放行，避免出口工具被自己的闸门挡住。
- UI：`webui` 顶栏「📋 计划中」角标 + 计划面板（`applyPlanState`），SSE 的 `种类:"计划"` 帧即时刷新。
- **与 `topdown` 解耦**：`topdown` 只提供提示词人格，不再自动打开计划模式；计划模式只认会话事件。

### 控制流向

- 会话级开关（`active`）→ 每轮把 `plan-mode` 的 section 注入系统提示 → Agent 只产计划、
  不执行改动，直到 `exit_plan_mode` 提交成功。原文判据：「Stay in plan mode until exit_plan_mode
  succeeds or the user switches the session mode.」
- **有中央规划器，但没有计划树**：规划器 = 提交出去的那份计划本体；`plan` 模式不按树推进叶子，
  它只把「执行」推迟到退出之后。
- 折叠方向：`折叠计划模式(事件, 截止)` 取 `[0, 截止)` 内最后一个 `plan/mode` 的 `active`；
  末个 `request/header` 处的状态由 `计划模式在末标题(事件)` 给出。

### 人机介入点

- **必须介入**：计划提交 = 用户预审点（`exit_plan_mode` 的批准）。**用户的对话式认可不算批准** ——
  包括回答你确认问题时的那句「对」：确认过的决定要折进计划、再从 `exit_plan_mode` 提交。
  这是 DSH section 原文的判据，不是礼貌约定。
- **可以介入**：用户可随时切会话模式退出 `plan`（等价于硬退出）。
- **一律不打断**：plan 模式下产计划的过程不请示；但任何实际改动在退出前都不允许发生。

### 输出形态

- **计划文档**：首标题即计划名（`首个标题(计划)` 取首个 markdown 标题，UI 用它做标题）；
  计划本体结构化提交，不做「边写边改」的草稿流。
- 客户端读的是投影值 `{active, pending}`（`投影视图(状态)`）：`pending = 期望 ≠ 当前 active`。

### 终止条件

- **正常终止**：`exit_plan_mode` 成功 → `plan` 退出，执行回到当前预设正常链路。
- **硬终止**：用户切会话模式（`plan/mode` 置 `active = 假`）；会话销毁。
- **预算上限 / 闸门**：未闭合轮次里发起的模式切换挂 `pending`（`有未闭合轮次(事件)`：
  `turn/start` 之后无 `turn/end` 即未闭合），命令失败不落状态 —— 不靠「下一轮再补」,
  避免同一轮内 `active` 与 `wanted` 打架。

### 实现要点

- 纯逻辑（复刻件，**不改**）：`src/计划模式.light` —— `校验配置` / `首个标题` / `折叠计划模式` /
  `有未闭合轮次` / `计划模式在末标题` / `投影初始` / `投影应用` / `投影视图`。
  上游是 `packages/plan/plan-mode/src/index.ts` 的纯逻辑核（Cordis Service 的 IO 胶水不复刻）。
- 提示文案：`src/预设组合.light` §1 `规划组行()`（当前 :44-47）里 `plan-mode` 行的
  `config.section`，组行 `planning` 由 `isolate.planMode` 隔离。
- 仍未接线（卡 T-0420）：`/plan` 命令注册、`exit_plan_mode` 工具、`plan` 投影到前端的
  事件帧。截至 T-0418，本仓现状 = 纯折叠逻辑 + 文案已经在手，没有任何一处把它们接到会话上。
- 刻意边界：`plan` 不占预设编号（不进 `组合清单()`、不进 `预设清单()`、不进设置页预设下拉）；
  纯逻辑层只折叠事件，不写注册表、不做 IO。

## 组合与切换

- **四个组合型模式不做互斥四选一**：会话可以在任意时刻切到另一个组合，工具集按
  `组合清单()` 的新条目重建（`预设切换` 负责切、`预设组合.组合(预设标识)` 负责取行表）。
  它们之间不是「选一个就锁死」，而是「当前会话用哪一份行表」。
- **模式状态默认会话级，不跨任务持久化**：新会话回到 `standard`；同一会话重启靠
  `session-modes.json` 的「模式 / 权限」两键恢复（#368 / `src/web服务器.light` 的会话预设）。
  没有任何「跨任务记住上次模式」的路径。
- **模式内部可嵌套，但嵌套不改顶层可见状态**：例如 `topdown` 推进某个叶子时局部切
  `brainstorm` 铺方案 —— 这是**执行层子 Agent 的行为**，子 Agent 按自己的预设组合拿工具集，
  顶层会话的模式 id、终止条件、用户可见的模式标签**都不变**。
- **两个行为型模式与组合型正交**：
  - `goal` 与组合型可并存，前提是该组合挂载 `tool-goal`（`bottomup` / `brainstorm` / `minimal`
    不带，故不并存）；
  - `plan` 与组合型正交：它只把「执行」推迟，不动工具集，任何挂载 `规划组行` 的预设都能开。
- **优先级**：显式切换 > 意图路由。用户手动切了模式之后，路由不再改写会话的预设 id；
  路由只在没有显式选择时生效。
