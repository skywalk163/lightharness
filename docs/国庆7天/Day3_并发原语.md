## 一、根因

- **现象**：lightharness 侧「并发」是靠**字典/双端队列 + 调用方手写循环**模拟出来的，
  语言层已有的 `异步 段落 / 等待 / 异步睡眠 / 创建任务 / 并发等待 / 首个完成`（`light-merge/src/code_generator.py:354-372`
  的 `# ---- A2-3 异步并发原语 ----` 段）**一个都没被调度层用过**。
- **定位路径**：先写 7 条只跑不改的探针，逐条排除 (a)「新语法不存在」与 (c)「原语名不对」，
  剩下 (b)。再 grep 出三模块的被引用面（代理循环 29 个文件 / 工具执行 30 个文件 / 任务拉取泵 1 个）
  评估迁移 blast radius。
- **根因（文件:行号）**：
  - `src/代理.light:179,403-418,452` —— inbox 用 `双端队列` 承载，「不引线程」。
  - `src/任务拉取泵.light:12-14` —— 轮询状态机被裁，交给宿主。
  - `src/工具执行.light:402` —— 执行器同步，无异步处理通道。
  - `src/代理循环.light:273` —— 派发同步串行，无协监听通道。

### B 方案的三条设计约束（为什么这样才无回归）

1. **新增而非替换**：`抽一轮` / `终抽` / `执行工具` / `派发监听` / `驱动` 全部原样保留，
   既有 29/30 个调用文件的行为逐字节不变。
2. **有状态的闸门必须串行**：`具并发执行` 把「权限 → 限流 → 取消」前置闸门做成**串行**，
   只把**已放行**的执行体并发。限流态（令牌桶余额 / 滑动窗口命中表）是有状态字典，
   逻辑时钟不推进 ⇒ B 的放行/拒绝判定与 A 逐请求相同（已由 A/B 用例实测审计条数一致）。
3. **不污染既有数据结构形状**：`代理循环` 的协监听表是**惰性建键**（首次注册时才
   `字典设置`），`建循环` 返回的 13 键字典形状与 A 完全一致 —— 用例里直接断言了
   `字典包含键(驱动, "协监听表") == 假`。

### 显式分流，不做运行期类型嗅探

`具登记异步处理` 走**显式登记**异步处理器，而不是在 `具并发执行体` 里嗅探返回值是不是协程。
理由：显式才可测、可审，不会让「同步工具被当成协程」这类静默假绿有藏身之处。
同步工具与异步工具在同一张注册表里用 `处理` / `异步处理` 两个字段并存。
