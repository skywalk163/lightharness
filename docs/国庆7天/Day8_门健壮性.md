### 1.2 根因（逐条一手实证，不是推测）

#### A. `test_concurrent_requests` —— 测试夹具是**单线程** HTTP 服务器

一手证据链：

| 证据 | 内容 | 日志 |
|---|---|---|
| ① 真实签名（v0.3.0 门日志） | `assert 9 == 10` | `lightharness/docs/国庆7天/Day2_异常处理后端收口.md:227` |
| ② 夹具实测类型 | `http.server.HTTPServer`（**非** `ThreadingHTTPServer`），`request_queue_size = 5` | `logs/day2/S1_probe_backlog.log` |
| ③ 探针复现真实签名 | CPU 满载下 30 轮 **2 轮红**，签名逐字相同 `len(results)==9` + `连接错误: 连接失败` | `logs/day2/S1_probe_decisive.log` |
| ④ 受控 A/B | **A 旧夹具 1/20 红；B 新夹具 0/20 红**（同一夹具、同一负载，仅切服务器类型） | `logs/day2/S1_probe_ab.log` |
| ⑤ 仓库内正确写法对照 | `tests/unit/test_原生腿_R13B_能力扩展.py:144` 用的是 `http.server.ThreadingHTTPServer` | — |

**机理**：`http.server.HTTPServer` 是**单线程**服务器——一次只处理一个连接，其余连接排在
`accept` 队列里，而该队列（`request_queue_size`）**默认只有 5**；用例一次并发 **10** 条。
本机隔离/低负载下服务端处理极快、连接即被 accept，队列从不溢出（这就是它长期「绿」的原因）；
一旦 CPU 被 xdist worker 挤满，服务端处理变慢 → **队列溢出 → 1 条连接被拒** →
被测客户端 `HTTP客户端.py` 默认 `max_retries=0`（`stdlib/lightpub/HTTP客户端.py:134`）**不重试**、
直接抛 `连接错误` → 该 worker 抛异常、`results` 少一条 → `assert 9 == 10`。

**归因判定**：这是**测试夹具的并发能力缺陷**，**不是**被测模块 `lightpub/HTTP客户端.py` 的缺陷
（真实客户端在真实服务器前不会被单线程 backlog 卡住）。故**只改夹具、不动被测代码**——
符合契约「不许改松断言」「不许改 stdlib 语义糊弄」两条禁止事项。

#### B. `test_并行批里一个抛异常其余两个照常回填` —— 绝对墙钟判据余量不足

一手证据链：

| 证据 | 内容 | 日志 |
|---|---|---|
| ① 原判据 | `assert 耗时 < 0.5`（单工具 `sleep=0.3`；并行期望 ≈0.30s、串行 ≈0.90s） | `tests/test_tool_parallel_light.py:262`(原行号) |
| ② 空载基线 | 40 次采样 **min 0.296 / 中位 0.297 / max 0.328** → 空载余量 1.7× | `logs/day2/S1_probe_timing_idle.log` |
| ③ **多进程**负载（模拟 xdist worker） | 8 个 burn 子进程 / 10 核 → 并行批 **0.500~0.844s（中位 0.555），20/20 轮全部超 0.5** | `logs/day2/S1_probe_timing_mp.log` |
| ④ 同场景串行基线 | **0.937 / 中位 0.946 / max 0.984** → 说明**实现从未真退化** | 同上 |
| ⑤ 负载模型对照 | 同进程 GIL 争抢（14 线程）会把耗时抬到 1.0~3.2s，是**过强**模型（真实门是**多进程**，不抢被测进程 GIL），故以 ③ 为准 | `logs/day2/S1_probe_timing.log` vs `S1_probe_timing_mp.log` |

**机理**：判据是**绝对墙钟上限**。`sleep(0.3)` 在 CPU 争抢下唤醒被整体拉长（实测 1.7~2.8×），
耗时从 0.30s 漂到 0.50~0.84s，**必然**越过 0.5；而同场景串行仍是 0.94~0.98s——
也就是说：**红的是判据，不是实现**。这正是台账 W-13 早已总结过的病症
（「脱离配置的魔数阈值」→ R95 改为「跑 5 次取 min/max、阈值锚定本测试配置」）。

**契约 §四.2 首选「断言不再依赖墙钟窗口」**，故本处采用更强的形态：把判据换成**离散的执行区间重叠**。

### 1.3 修复（确定性，断言语义一字未削弱）

**修复 A**：`tests/test_http_client.py:184`（夹具）
```python
# 原：
self._server = http.server.HTTPServer((self.host, self.port), _Handler)
# 改为：
self._server = http.server.ThreadingHTTPServer((self.host, self.port), _Handler)
```
外加 6 行注释说明「为什么必须 Threading + 为什么单线程是标准库语义而非被测模块缺陷」。
**`test_concurrent_requests` 用例本体一字未改**（`assert len(results) == 10` 原样保留）。

**修复 B**：`tests/test_tool_parallel_light.py::Test失败隔离::test_并行批里一个抛异常其余两个照常回填`
- 新增助记 `_记时工具(名字, 区间)`（与 `_睡工具` 同语义，额外记录本次执行的 `[起, 止]`）；
- 判据由 **`耗时 < 0.5`（绝对墙钟）** 改为 **「执行区间重叠 + 宽松上界」双判据**：
```python
隔 = min(区间["ok1"][1], 区间["ok2"][1]) - max(区间["ok1"][0], 区间["ok2"][0])
assert 隔 > 0, "…整批退化成串行了：ok1 与 ok2 的执行区间不重叠（隔 %.3fs）" % 隔
assert 耗时 < 睡 * 3, "…整批退化成串行了（耗时 %.3fs）" % 耗时
```
- **为什么这不是「改松断言」**（契约 §十.1 的红线）：
  - 语义上**更严**：原判据只在**单工具**场景下要求「比串行快」；新判据直接断言
    「**两个只读项确实同时在跑**」（区间重叠），它**真的可证伪**——实测强制串行时重叠 = **−0.296s**；
  - 区间重叠是**离散位**（只看执行次序，不看耗时长短）→ 对 CPU 负载**天然免疫**；
  - 保留 `耗时 < 睡*3` 兜住「整体退化成串行」（串行 0.9s > 0.9s 边界会红）。
- 被保留的断言语义（回填顺序、失败项可读文本、异常信息不吞成空串）**一字未动**。

## 二、S2 · #75 补进宿主冒烟生成链（**降级出口**）

### 2.1 目标与已核实事实

开工前实测复现了「74」：

| 事实 | 实测值 | 证据 |
|---|---|---|
| 磁盘插件目录数 | **75** | `ls 插件/ \| wc -l` = 75 |
| 生成器 `插件清单()` | 动态枚举，**已能返回 75** | `集成/生成宿主冒烟.py:31-40`；探针输出「目录总数 75 / 清单内 75 / 被排除 0」 |
| 生成物 **是陈旧快照** | 导入 74 行、挂载 74 行、硬编码 `打印 74`，**0 处**「语音远端控制器」 | `集成/宿主冒烟.light:78`（导入止于 #74）、`:479`（`打印 74`） |
| 生成器里 74 **不是硬编码** | 挂载数取 `str(len(清单))`（`集成/生成宿主冒烟.py:310`） | 满足契约 §六.3 |

→ 说明「74」的来源**不是生成器漏枚举，而是生成物停留在加 #75 之前的版本**。按契约 §四.3「用生成器重生成」。

### 2.2 尝试纳入 #75 时暴露的**真障碍**（第 1 层：挂载签名）

重生成后确实得到 75/75，但运行宿主冒烟立即报错——**#75 与其余 74 个插件的挂载契约不同**：

```
错误: 类型错误
  类型错误：挂载() missing 1 required positional argument: '识别器通道'（宿主冒烟:168）
```

全插件扫描证实 #75 是**唯一**例外（`挂载` 第二参**无默认值**）：

| 挂载签名形态 | 插件数 | 例 |
|---|---|---|
| `段落 挂载(注册表)` | 63 | 绝大多数 |
| `段落 挂载(注册表, X=空)` | 11 | 三维生成/图片生成/视频生成/语音转文字/运行检视器… |
| **`段落 挂载(注册表, 识别器通道)`（无默认值）** | **1（#75）** | 语音远端控制器 |

生成链补一行「带参数调用」看似可解（注入 `["snapshot": 空]`）。**但继续验证时撞上第 2 层障碍。**

### 2.3 真障碍（第 2 层，决定性）：**#75 用错了注册表接口**

按「生成链补参数」改完并重生成后，宿主冒烟**仍然失败**：

```
错误: 属性错误
  类 工具注册表 缺少方法/属性 append（…\语音远端控制器.light:284）
  （Python 原始错误：'工具注册表' object has no attribute 'append'）
```

一手证据：

| 证据 | 内容 |
|---|---|
| #75 挂载实现 | `段落 挂载(注册表, 识别器通道)` → `注册表.追加(快照绳)`（`插件/语音远端控制器/语音远端控制器.light:284`） |
| 宿主冒烟传入的注册表 | `设 注册表 为 新建 工具注册表()`（`集成/生成宿主冒烟.py:102`） |
| `工具注册表` 的方法面 | 只有 `构造 / 注册 / 注销 / 有无 / 名单 / 查找 / 描述表` 等——**没有 `追加`**（`lightharness/src/工具.light:477+`） |
| `追加` 的归属 | cordis **绳表**语义（`绳构造注册` 造「绳」，`绳归一提供者` 里 `表.追加(...)`，`lightharness/src/toolcordis.light:73,86`） |
| 旁证：仓库自己早已知情 | `集成/生产挂载.light:14` 原文：「平挂载 `.挂载(注册表)`（各插件默认参兜底，**语音远端控制器 因必填第二参本就不在清单**）」 |

**结论（归因）**：#75 的 `挂载` 是按 **cordis 绳注册表**写的（`追加` 一条「绳」），
而宿主冒烟（以及 `生产挂载.light`）传的是 **工具注册表**（`注册(定义)`）。
**两套注册表接口不同 → #75 挂不进任何工具注册表**，且这与「必填第二参」是**两个独立障碍**。

**这不是「生成链漏一行」，而是 #75 插件本身的接口缺陷**（或其 cordis 绳注册尚未接入宿主装配路径）。
因此 Day7「仅缺一行 import+挂载」的描述**不准确**——它是 v0.3.0 把 #75 排除在 74 之外的真实原因，
只是当时没查到这一层。
