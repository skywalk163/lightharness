## 一、S1 修复的独立复验

### 1.1 面① 断言强度审计（静态逐条比对，S1 未做此面）

方法：从 git blob 取 **修复前 `d6b84a716`** 与 **修复后 `dac6bea1e`** 的源码，
用 `ast` 解析出两条用例的全部 `assert` 语句，逐条对照（**不跑测试、只看源码**）。

脚本：`logs/day2/S8_assertion_audit.py`｜输出：`logs/day2/S8_assertion_audit.log`

| 用例 | 改前断言 | 改后断言 | 逐字保留 | 被删除/削弱 |
|---|---|---|---|---|
| `test_concurrent_requests` | 3 | 3 | **3/3** | **0** |
| `test_并行批里一个抛异常其余两个照常回填` | 6 | 7 | **5/6** | 1（`耗时 < 0.5`，见下） |

```
文件: tests/test_http_client.py     用例: test_concurrent_requests
  改前 3 条 → 改后 3 条，逐字相同：
    len(results) == 10 / all((r == 200 for r in results)) / len(errors) == 0
  >>> 改前断言被删除/削弱的条数: 0

文件: tests/test_tool_parallel_light.py  用例: test_并行批里一个抛异常其余两个照常回填
  改前 6 条 → 改后 7 条；其中 5 条逐字保留（回填顺序、ok1/ok2 内容、失败可读文本、异常原文）
  >>> 改前断言被删除/削弱的条数: 1 ['耗时 < 0.5']
```

**对那条唯一变动的独立判定**（S8 的职责，不是复述 S1 结论）：

| 维度 | 原 `耗时 < 0.5` | 新 `隔 > 0` + `耗时 < 睡*3` |
|---|---|---|
| 判的是什么 | 一个**绝对时间上限** | **两个只读项是否真的同时在跑**（执行区间重叠） |
| 负载敏感 | **敏感**（实测多进程 8/10 核即 20/20 轮 0.50~0.84s → 必红） | **不敏感**（离散位：只看次序，不看耗时长短） |
| 可证伪性 | 弱（「没退化」只能靠时间间接推） | **强**（真串行时重叠为负，实测 −0.296s） |
| 是否放宽 | — | **不是**：对「没退化」的要求由「间接推断」升为「直接断言」 |

→ **独立结论：该变更属「判据形态升级」，不构成断言语义削弱。**
（并保留 `耗时 < 睡*3` 兜住「整批退化成串行」，与 §1.2 的反跑互证。）

### 1.2 面② 真实历史代码 A/B（独立于 S1 的方法）

S1 的反跑用的是 **monkeypatch**（在内存里把夹具类型换掉）；S8 改用一个**更硬**的方法：
用 `git worktree add <scratch> d6b84a716` 检出**真实的修复前代码树**，与主树（`dac6bea1e`）
在同一负载下逐轮对照。**两条路互相独立，结论一致才算复验成立。**

**(a) 用例级 A/B（8 进程负载，各 10 轮）** — 脚本 `S8_ab_real.py`｜日志 `S8_ab_real.log`

| 被试用例 | A 旧树 `d6b84a716` | B 新树 `dac6bea1e` |
|---|---|---|
| `test_并行批里一个抛异常其余两个照常回填` | **通过 9 / 失败 1** ← 复现 | **通过 10 / 失败 0** |
| `test_concurrent_requests` | 通过 10 | 通过 10（8 进程负载下未复现，见 (b)） |

> `test_并行批…` 的旧树失败即 S1 所报的**绝对判据假红形态**：实现没退化，是判据先红。
> 这独立验证了「红的是判据不是实现」这一 S1 结论。

**(b) 夹具并发容量 A/B（判决性，确定性有界）** — 脚本 `S8_ab_http_capacity.py`｜日志 `S8_ab_http_capacity.log`

方法：用夹具自带的 `/slow` 端点（服务端 `sleep 0.5s`），10 条并发测**总墙钟**。
若夹具串行 → 10×0.5 ≈ 5s；若夹具真并发 → ≈ 0.5s。**分离度 ~10×，完全确定性、有界。**

```
[A旧] 夹具=HTTPServer         backlog=5 | 10 并发 /slow(0.5s) 3 轮 = 5.04 / 5.03 / 5.03 | 中位 5.03s
[B新] 夹具=ThreadingHTTPServer backlog=5 | 10 并发 /slow(0.5s) 3 轮 = 0.52 / 1.04 / 0.52 | 中位 0.52s
=== A 旧夹具 5.03s | B 新夹具 0.52s | 提速 9.6x ===
```

→ **直接量化了 S1 认作真因的那个属性**：旧夹具的**并发承载能力为零**（10 条请求被完全串行化，
墙钟恰为 10×0.5s），新夹具真并发。这是对 S1 根因（「夹具单线程 → 队列溢出 → 1 条被拒 →
`assert 9 == 10`」）的**独立、可复现、确定性**证明。

> **为什么 HTTP 这条在进程负载下不红、而在这里红**：该缺陷需要的是**进程内连接并发**
> （10 条线程同时连），xdist 多进程负载只争 CPU、并不制造额外连接；而且队列溢出要求
> 「服务端处理慢到让 10 条连接同时积压」——本机磁盘/CPU 太快，窗口很窄。
> → 这解释了它为何长期以 **flaky**（而非稳定红）的面貌存在，也说明**必须用定向方法**（本节的容量法）
> 而非「重跑几遍」来复验它。**S1 与 S8 在这一点的判断一致。**

### 1.3 面③ 受载 ×10 复跑（S1 是空载 ×10，本面换条件）

方法：把两条用例放在**多进程负载**下各跑 10~12 轮（`-o addopts=` 隔离口径），
负载强度取 **8 / 12 进程**两档（12 > 物理核 10）。

| 负载 | 轮数 | `test_并行批…` | `test_concurrent_requests` | 日志 |
|---|---|---|---|---|
| 8 进程 | 各 10 轮 | **A 旧树 9 通过 / 1 失败** → **B 新树 10/10 通过** | A 旧树 10/10、B 新树 10/10（未复现） | `S8_ab_real.log` |
| 12 进程 | 12 轮 | — | **A 旧树 12/12、B 新树 12/12**（未复现） | `S8_ab_http_heavy.log` |

**读法（重要，避免过度声明）**：
- `test_并行批…` 这一面**对照成立**：同负载下旧树复红、新树全绿 → 修复有效。
- `test_concurrent_requests` 在两档**进程**负载下**都没复现**（A 旧树 22 轮全绿）。
  这与 §1.2-(b) 的判定一致：**该缺陷需要进程内连接并发，多进程序负载不制造连接**，
  所以「进程负载下不红」**不等于**「旧代码没问题」——§1.2-(b) 的容量法才是它的定向证据。
  此处**不声称**「受载 ×10 复现并修复」，只声称「修复后在受载条件下不红」。
- 另有两次**同进程争抢探针**（14 / 20 线程）**超时未完成**（旧夹具下连接被受理却不被服务、
  客户端无 socket 超时 → 永久阻塞）。这不是「跑绿了」，而是**旧夹具的又一失败形态**；
  其有界化后的替代证据即 §1.2-(b) 的容量法。超时日志：`S8_ab_http_sameproc.log`（仅表头）。

### 2.3 本轮最重要的发现：**这个指标不可跨会话引用绝对值**

三个来源、**同一台 Windows 开发机**：

| 来源 | 冷 每例 | 温 每例 | 提速 |
|---|---|---|---|
| `compiler_bench.py` docstring 原自述（**估算**） | 4.6s | 0.5s | ≈8× |
| `Day6_freebsd_phaseB2.md` §3.6（v0.3.0 实跑） | 3.26s | 0.30s | 11.0× |
| **S8 固化（本次 5 轮中位）** | **0.94s** | **0.11s** | **8.6×** |

→ 冷启动绝对值 **0.94s ~ 4.6s，相差近 5×**；就算只取两次「实跑」，**0.94s vs 3.26s 也差 3.5×**。

**机理**：冷启动耗时的**主体是「拉起解释器 + 重新 import 整条编译器栈」的固定开销**
（§1.3 反跑已定量：重付一次 import ≈ 0.7s）。这部分**完全由机器瞬时状态支配**——
杀软扫描、磁盘缓存冷热、其他 agent 子任务的 CPU 占用、`__pycache__` 是否已就位，
都会成倍影响它。**温解释器侧的耗时（≈0.1s）反而稳定**（5 轮全为 0.11s）。

**因此固化的是「方法 + 量级」，不是「那个数字」**：
- ✅ 稳定结论：温缓存带来 **≈8~11×** 的量级提升；杠杆在「解释器常驻」而非「缓存 .py 产物」；
- ❌ 不可引用：任何**绝对值**（0.94 / 3.26 / 4.6 / 15s）都不应跨会话、跨机器直接比较；
- 📌 用法：要比较，**必须在同一次会话、同一负载下当场跑**（脚本已支持 `python scripts/compiler_bench.py <n>`）。

## 三、反跑判据：破坏温缓存命中路径 → 冷/温耗时差应消失

契约（计划 §三 L3）反跑判据原文：**「破坏温缓存命中路径 → 冷/温耗时差消失」**。

脚本：`logs/day2/S8_antirun_warm3.py`｜日志：`logs/day2/S8_antirun_warm.log`

**方法**（前两版探针失败的过程也留档，见 §3.2）：在**任何 light 侧 import 之前**对 `sys.modules`
拍下原始快照（本次 85 个模块）；反跑时把快照之后新增的模块**全部剔除**，
强制每例重付整条 import 链。

| 情形 | 每例耗时 | 冷/温速度比 | 单例明细 |
|---|---|---|---|
| ① 正常温（缓存命中） | **0.125s** | **8.84×** | 0.470 / 0.010 / 0.010 / 0.009 |
| ② **反跑·每例重付 import** | **0.704s** | **1.57×** ← 差值几乎消失 | 0.584 / 0.660 / 0.727 / 0.844 |
| ③ 恢复（缓存命中） | 0.206s | 5.34× | 0.796 / 0.010 / 0.009 / 0.010 |

（冷基线：每例 1.103s）

**判定：反跑成立** ——
- ②把「温缓存」这个变量破坏掉之后，每例耗时从 0.010s 涨到 0.58~0.84s（**≈冷启动价**），
  与冷基线的比值从 **8.84× 塌到 1.57×** → **「冷/温耗时差」确实由这条路径产生**；
- ③关掉破坏后单例回到 0.010s → **差值恢复**，双向成立。

### 3.2 探针迭代留档（如实记录两次失败，因为「为什么失败」本身是结论）

| 版本 | 做法 | 结果 | 失败原因 |
|---|---|---|---|
| v1 | 每例只 `pop` 顶层模块名再 `exec_module` | 反跑后反而更快（117×） | Python 会复用已缓存的**子模块** → 「重导入」几乎免费 |
| v2 | 快照取在**已经 import 过**之后 | ①=②=③（反跑未生效） | 剔除集合为空 → 没真破坏 |
| **v3** | 快照取在**任何导入之前**，反跑剔除**全部新增模块** | **① 8.84× → ② 1.57× → ③ 恢复** | ✅ 成立 |

→ 这条迭代本身印证了 §2.3 的机理：**温缓存的收益几乎全在「避免重复 import」**，
所以只有把整条 import 链剔除，才测得出来。
