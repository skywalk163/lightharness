## 四、本子任务要补的 4 块

### 4.1 打标流程（可复现）

- 三仓 `v0.4.0-rc2` 的切出时机（**T1/T2 收口 + 复核通过之后**）、命令、**打标前必须干净**（工作树无未提交）、**tag 与 HEAD 一致性校验**。
- annotated vs lightweight 的选择与理由。
- **已存在 tag 时的处置**：**不移动已推 tag** 是铁律；rc1 若已在某远端存在，**不得改写**，只能新增 rc2。

### 4.2 远端 tag 推送 runbook（**§8.2 的落地**）

- **逐 `(repo, remote, ref)` 一条命令**，**10 个落点逐项点名**：
  - LH：`github` / `myrepo` / **`origin`（=gitcode，注意远端名不叫 `gitcode`）**
  - LP：`github` / `gitcode` / `gitea`
  - LM：`github` / `gitcode` / **`origin`（=本地 `g:\github\light`）** / `gitea`
- 每条附：**预期输出**、**失败模式**、**复核命令**。
- **§8.2 铁律**：禁止 `git push | tail`（`$?` 是 tail 的 rc 恒 0 → 假成功）；复核必须**逐项**；github/gitcode 走 **API**（本机 git 协议不可达、API 可达）。
- **§8.1 铁律**：github 侧上传走 `lightharness/_push_github_tree_sync.py`（**原样字节，禁 CRLF→LF**）。

### 4.3 回滚预案

- 按失败类给出动作：**tag 推错远端** / **推了错误的 commit** / **github tree 与本地不等价（CRLF 回归）** / **PyPI 版本已占用**。
- 明确**可回滚**与**不可回滚**（PyPI 已发版本通常不可撤回 → 只能 yank / 发补丁版）；**不移动已推 tag**（必要时发新 tag）。
- 给出**验证回滚完成**的命令。

### 4.4 发布前检查单（一页，等示意时照着跑）

- 把 4.1–4.3 + T4 的预检 + `Day11 §二` 的用户密钥清单，合成**一张可打勾的检查单**（按顺序，每步带「通过判据」与「不通过怎么办」）。

## 八、验收标准（可量化）

1. **10 个落点逐项**出现在 runbook，**远端名与实测一致**（LH `origin`=gitcode 必须体现）。
2. 每条推送命令带**预期输出 + 失败模式 + 复核命令**；明确**禁止** `push | tail`。
3. **回滚预案**覆盖 §4.3 的 4 类失败，区分可/不可回滚，含验证命令。
4. **发布物 = `v0.4.0-rc2`** 写明；**rc1 标注「仅留档、不作发布物」**；**检查单第一步**是「校验发布物是否包含 T1/T2」。
5. 干跑自检 + **反向自检**都有记录。
6. **无任何 token / 密钥值**出现在文档/日志。
7. 四件套齐全。

## 九、反跑判据

1. 用 runbook 命令做干跑 → 每条都能得到「预期输出」描述的结果（或明确的失败模式），**不需要临场猜**。
2. **反向自检**：把 LH gitcode 远端名写成 `gitcode` → 逐项点名机制应暴露它。
3. 故意把 `push | tail` 写进 runbook → 应被「禁止项自检」拦下。
