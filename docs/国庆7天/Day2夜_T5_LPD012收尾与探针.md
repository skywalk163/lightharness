## 三、容量型探针（`probes/lp012_capacity_连接并发.py`，遗留 #3 的交付）

### 3.1 为什么通用手段无效（引用契约 §三-3）

`test_concurrent_requests` 是**连接并发**类缺陷：多个并发请求被服务端**逐个串行消费**，
「重跑几次 / 加进程负载」不会改变串行排队的事实，判不出来；只有**定向容量法**能测出：
N 个并发打 `/slow`（服务端每次延时 D），墙钟 T 若 ≈ N×D 说明被串行化（缺陷形态复现）。

### 3.2 探针形态与自检设计

- **纯标准库实现**（`http.server` + `threading` + `urllib.request`），适配 .82 无 requests 的环境。
- **三态退出码**：`0=通过`（T/D≈1×，并发正常）/ `1=触发`（T/D≈N×，串行化形态复现）/ `2=探针无效`。
- **自检设计**（直接源自 Day10 §3.2 两次失败的教训：v2 剔除集合为空 → 反跑未生效）：
  - `--空剔除`：人为注入**空剔除集合** → 必须报「探针无效（dc=2）」而不是通过；
  - 并发数 <1（0 请求）→ 报「探针无效」；
  - 全部请求失败 → 报「探针无效」。
- **判定阈值**：`T/D ≤ 1.5×` → 通过；`T/D ≥ 0.5·N×` → 触发；介于两者之间 → 灰区（dc=3，不冒充结论）。

### 3.3 .82 实测（两侧 + 自检，各留日志）

| 场景 | 命令（参数） | T/D | 判定 | rc |
|---|---|---|---|---|
| 压满（缺陷形态复现） | `--服务端 串行 --并发 10 --慢秒 0.3` | **9.09×** | **触发** | 1 |
| 无压力（契约 §八-2 应通过） | `--服务端 串行 --并发 1 --慢秒 0.3` | 1.01× | 通过 | 0 |
| 正常形态 | `--服务端 线程化 --并发 10 --慢秒 0.3` | 1.06× | 通过 | 0 |
| 正常形态（复跑 #2，验稳定性） | 同上 | 1.06× | 通过 | 0 |
| 自检：空剔除集合（契约 §八-3） | `--并发 10 --空剔除` | — | **探针无效** | 2 |

**复跑稳定性**：正常形态跑 2 次结论一致（1.06× / 1.06×，均为通过）。
